1. 全景概览：记忆系统的三层架构

Claude Code 的记忆系统并非单一机制，而是由三个互补层组成的架构：

📝 CLAUDE.md (指令层)
  • 管理方: 用户直接编辑
  • 用途: 项目规范、编码约定
  • 存储: 项目目录内，可 Git 提交
  • 加载: 作为 User Context 注入
  • 来源: Managed / User / Project / Local
🤖 Auto Memory (自动记忆层)
  • 管理方: AI 自动写入
  • 用途: 用户偏好、反馈、项目上下文

  • 加载: System Prompt + 按需召回

2. 路径解析：记忆文件存在哪里

2.1 Auto Memory 目录路径

核心函数 getAutoMemPath() 在 src/memdir/paths.ts:223 中定义，使用 memoize 缓存：

// src/memdir/paths.ts
export const getAutoMemPath = memoize(
  (): string => {
    // 优先级 1: 环境变量覆盖 (Cowork 场景)
    const override = getAutoMemPathOverride() ?? getAutoMemPathSetting()
    if (override) return override

    // 优先级 2: 默认路径
    const projectsDir = join(getMemoryBaseDir(), 'projects')
    return (
      join(projectsDir, sanitizePath(getAutoMemBase()), 'memory') + sep
    ).normalize('NFC')
  },
  () => getProjectRoot(),  // 缓存键
)

路径解析优先级（第一个命中的生效）：

3. 文件格式：记忆长什么样

3.1 单个记忆文件格式

每个记忆文件使用 YAML frontmatter + Markdown 正文的格式，在 src/memdir/memoryTypes.ts:261 中定义了模板：

---
name: 用户角色
description: 用户是一名资深前端工程师，主要使用 React 和 TypeScript
type: user
---

用户有 10 年前端经验，精通 React/TypeScript。
最近在学习 Rust 用于 CLI 工具开发。
偏好函数式编程风格，不喜欢 class 组件。

3.2 四类型分类体系

记忆被严格约束为四种类型（src/memdir/memoryTypes.ts:14），每种类型有明确的适用范围：

类型标签含义何时保存示例
user user 用户的角色、目标、知识水平 了解到用户的背景信息时 "用户是数据科学家，正在调查日志系统"
feedback feedback 用户对工作方式的指导（纠正+确认） 用户纠正或确认非显而易见的做法时 "不要在测试中 mock 数据库——上次出过问题"
project project 项目上下文：目标、截止日期、决策 了解到代码/历史中不可推导的项目信息时 "周四之后冻结非关键合并——移动端在切分支"
reference reference 外部系统的指引（Linear、Grafana 等） 了解到外部资源的位置和用途时 "pipeline bug 在 Linear 的 INGEST 项目中追踪"
feedback 类型的特殊结构: 系统要求 feedback 类型的记忆按 规则 → Why → How to apply 三段式组织，这样未来的 AI 能判断边缘情况，而不是盲目执行规则。

3.3 MEMORY.md 索引文件

MEMORY.md 是记忆目录的索引文件，不是记忆本身。格式为纯 Markdown，每行一条：

- [用户角色](user_role.md) — 前端工程师，React/TS 专家
- [测试规范](feedback_testing.md) — 必须用真实数据库，不能 mock
- [部署流程](project_deploy.md) — 通过 #deploy-queue 频道审批
- [Linear 项目](reference_linear.md) — pipeline bugs 在 INGEST 项目

限制（src/memdir/memdir.ts:35-38）：

  • 最多 200 行（MAX_ENTRYPOINT_LINES）
  • 最多 25KB（MAX_ENTRYPOINT_BYTES）
  • 超限时自动截断并附加警告信息

3.4 Frontmatter 解析

Frontmatter 由 src/utils/frontmatterParser.ts 中的 parseFrontmatter() 函数解析：

// src/utils/frontmatterParser.ts
export function parseFrontmatter(
  markdown: string,
  sourcePath?: string,
): ParsedMarkdown {
  // 1. 用正则匹配 --- 之间的内容
  const match = markdown.match(/^---\s*\n([\s\S]*?)---\s*\n?/)
  if (!match) return { frontmatter: {}, content: markdown }

  // 2. 用 YAML 解析器解析
  let frontmatter = parseYaml(match[1])

  // 3. 如果失败，尝试自动引用特殊字符后重试
  if (!frontmatter) {
    frontmatter = parseYaml(quoteProblematicValues(match[1]))
  }

  return { frontmatter, content: markdown.slice(match[0].length) }
}

// src/memdir/memdir.ts — loadMemoryPrompt() 简化版
export async function loadMemoryPrompt(): Promise<string | null> {
  // 1. 检查是否启用自动记忆
  if (!isAutoMemoryEnabled()) return null

  // 2. KAIROS 模式 → 日志范式
  if (feature('KAIROS') && getKairosActive()) {
    return buildAssistantDailyLogPrompt()
  }

  // 3. Team Memory 模式 → 合并提示
  if (feature('TEAMMEM') && isTeamMemoryEnabled()) {
    await ensureMemoryDirExists(teamDir)
    return buildCombinedMemoryPrompt()
  }

  // 4. 标准 Auto Memory 模式

  return buildMemoryLines('auto memory', autoDir).join('\n')
}

4.3 路径 C: 按需召回 (Relevant Memories)

这是最智能的一条路径。当用户发送消息时，系统异步查找最相关的记忆文件：

// src/utils/attachments.ts — startRelevantMemoryPrefetch()
// 用户发送消息时触发

1. startRelevantMemoryPrefetch()
2.   → findRelevantMemories(query, memoryDir)     // src/memdir/findRelevantMemories.ts
3.     → scanMemoryFiles(memoryDir)                // 扫描所有 .md 文件的 frontmatter
4.     → selectRelevantMemories(query, memories)   // 调用 Sonnet 选择最相关的
5.   → readMemoriesForSurfacing(selected)           // 读取文件内容
6.   → memoryFilesToAttachments(memories)           // 转为 attachment
7. → 渲染为 <system-reminder> 包裹的用户消息

具体实现在 src/memdir/findRelevantMemories.ts:39：

// src/memdir/findRelevantMemories.ts
export async function findRelevantMemories(
  query: string,
  memoryDir: string,
  signal: AbortSignal,
  recentTools: readonly string[] = [],
  alreadySurfaced: ReadonlySet<string> = new Set(),

  // 1. 扫描记忆目录，获取所有 .md 文件的 frontmatter
  const memories = (await scanMemoryFiles(memoryDir, signal))
    .filter(m => !alreadySurfaced.has(m.filePath))

  // 2. 调用 Sonnet 侧查询选择最相关的（最多 5 个）
  const selectedFilenames = await selectRelevantMemories(
    query, memories, signal, recentTools,
  )

  // 3. 返回路径 + mtime
  return selected.map(m => ({ path: m.filePath, mtimeMs: m.mtimeMs }))
}

侧查询的系统提示（src/memdir/findRelevantMemories.ts:18）要求 Sonnet：

  • 只选择确定有用的记忆，不确定就不选
  • 最多返回 5 个文件名
  • 如果用户正在使用某个工具，不要选该工具的使用文档（但要选已知问题/注意事项）
  • 可以返回空列表

4.4 记忆新鲜度提示

src/memdir/memoryAge.ts 提供了记忆年龄的计算和过时警告：

// src/memdir/memoryAge.ts
export function memoryAge(mtimeMs: number): string {
  const d = memoryAgeDays(mtimeMs)
  if (d === 0) return 'today'
  if (d === 1) return 'yesterday'
  return `${d} days ago`
}

export function memoryFreshnessText(mtimeMs: number): string {
  const d = memoryAgeDays(mtimeMs)
  if (d <= 1) return ''
  return `This memory is ${d} days old. ` +
    `Memories are point-in-time observations, not live state — ` +
    `claims about code behavior or file:line citations may be outdated. ` +
    `Verify against current code before asserting as fact.`
}

超过 1 天的记忆会自动附加过时警告，防止 AI 把过时信息当作当前事实。

8.1 Dream 是什么

"Dream"（做梦）是一个记忆整合过程——AI 回顾所有记忆文件，合并重复项、修复过时信息、清理索引。灵感来自人类睡眠时的记忆整合。

Phase 4 — Prune and index（修剪与索引）
  • 更新 MEMORY.md，保持在 200 行 / 25KB 以内

export function isAutoMemoryEnabled(): boolean {
  // 优先级 1: 环境变量强制关闭
  if (isEnvTruthy(process.env.CLAUDE_CODE_DISABLE_AUTO_MEMORY)) return false

  // 优先级 2: 环境变量强制开启
  if (isEnvDefinedFalsy(process.env.CLAUDE_CODE_DISABLE_AUTO_MEMORY)) return true

  // 优先级 3: --bare 模式关闭
  if (isEnvTruthy(process.env.CLAUDE_CODE_SIMPLE)) return false

  // 优先级 4: CCR 无持久存储时关闭
  if (isRemoteMode && !hasRemoteMemoryDir) return false

  // 优先级 5: settings.json 配置
  const settings = getInitialSettings()
  if (settings.autoMemoryEnabled !== undefined) return settings.autoMemoryEnabled

  // 默认: 开启
  return true
}

15. 常见问题

Q: CLAUDE.md 和 Auto Memory 会冲突吗？

不会。系统有明确的"不要保存"规则："Anything already documented in CLAUDE.md files." CLAUDE.md 是用户主动写的指令，Auto Memory 是 AI 自己学到的知识，两者有不同的语义。如果有冲突，CLAUDE.md 优先级更高（因为它在 User Context 中加载得更晚，模型对后加载的内容关注度更高）。

Q: MEMORY.md 超过 200 行会怎样？

自动截断。函数 truncateEntrypointContent() 会先按行截断，再按字节截断（25KB），并在末尾附加警告信息。被截断的部分不会丢失——它们仍然在磁盘上的文件中，只是不会被加载到上下文里。

Q: 后台提取 Agent 和主 Agent 会同时写记忆吗？

不会。有互斥机制：hasMemoryWritesSince() 会检查主 Agent 是否已在当前轮次写入过记忆文件。如果主 Agent 已写，后台提取会跳过该轮次。

Q: 记忆文件有大小限制吗？

单个记忆文件没有硬限制，但 MEMORY.md 索引有 200 行 / 25KB 的限制。Session Memory 有 MAX_SECTION_LENGTH = 2000 字符和 MAX_TOTAL_SESSION_MEMORY_TOKENS = 12000 token 的限制。

Q: 为什么有些记忆没有被召回？

Sonnet 侧查询是保守的——它只选择"确定有用"的记忆。如果记忆的 description 字段写得不够具体，或者与当前查询的关联不明显，就不会被选中。建议在 description 中写清楚记忆的使用场景。

Q: /remember 和 /dream 有什么区别？

/remember 是审查和整理——它只提出建议，不自动修改文件。目的是把自动记忆"晋升"到 CLAUDE.md 等更持久的位置。
/dream 是整合和清理——它会实际修改文件，合并重复项、修复过时信息、修剪索引。相当于 AI 的"大扫除"。

Q: KAIROS 模式有什么不同？

KAIROS 是"助手模式"（长时间运行的会话），记忆采用追加日志范式：AI 将记忆追加到 logs/YYYY/MM/YYYY-MM-DD.md 文件中，而不是维护 MEMORY.md 索引。每晚的 /dream 会将日志蒸馏为主题文件 + MEMORY.md。

! 本节是「标注内容」，是阅读过程中识别出的疑惑点与澄清。 视觉上与原文档（冷色调蓝紫）区分：标注区采用暖色调（橙色/红色），且有独立边框、顶部横幅和样式覆写。原文内容保持原样未修改。

🟦 类别一：运行时与环境

❓ 疑惑 1: import { feature } from 'bun:bundle' 是什么？

困惑点: 前端工程师熟悉的 import 都是 npm 包名,没见过 bun: 这种前缀。

澄清: Bun 运行时（不是 Node.js！）内置了一些伪模块：

  • bun:bundle — 编译时注入的常量,被 Bun 的打包器特殊处理
  • bun:ffi — 调用 C 语言原生库

类比: 类似 webpack 的 process.env.NODE_ENV,但更底层——在编译时直接做条件消除（tree-shaking）。如果 feature('KAIROS') 在编译时被设为 false,整个分支代码会被直接删掉,产物里看不到这些代码。

❓ 疑惑 2: 为什么要用 Bun 而不是 Node.js？

澄清: Bun (https://bun.sh) 是一个用 Zig 写的 JavaScript 运行时,卖点是启动快、原生支持 TypeScript、内置打包器。Claude Code 选择 Bun 是因为：

  • 启动 cli.tsx 这样的入口文件几乎无延迟
  • 内置的 Bun.build() 可以做代码分割
  • bun:bundle 这种伪模块支持编译时宏,对条件编译很友好

前端类比: 类似 Vite vs Webpack 的差别——Bun 是一个 all-in-one 工具链。

❓ 疑惑 3: --bare 模式是什么?

澄清: --bare 是 Claude Code 的一个命令行参数,意为"极简模式"。开启后:

  • 不加载 CLAUDE.md
  • 不加载 Auto Memory
  • 不启动后台提取

设计意图:给 CI/CD、自动化脚本、纯管道使用(echo "..." | claude -p)用的——这些场景下不需要任何个性化记忆。

❓ 疑惑 4: 什么是 CCR?

澄清: CLAUDE_CODE_REMOTE 环境变量,意为 "Claude Code Remote"——可能是 Anthropic 的某个远程部署服务(代码里没有详细解释)。当处于 CCR 模式且没有 CLAUDE_CODE_REMOTE_MEMORY_DIR 时,自动记忆会被禁用(因为远程环境无持久化)。

🟧 类别二:系统级概念

❓ 疑惑 5: realpath、lstat、symlink 是什么?

澄清: 这些是 Unix/Linux 文件系统调用,前端工程师很少接触:

系统调用作用前端类比
realpath(path)解析所有符号链接,返回真实路径类似 path.resolve() 但会跟踪 symlink
lstat(path)读取文件元数据(不跟随 symlink)类似 fs.stat() 但不 follow link
symlink软链接(类似 Windows 快捷方式)前端没对应概念,系统级概念

为什么记忆系统关心这些: 防止攻击者在记忆目录里放一个 team/secret → ~/.ssh/authorized_keys 的符号链接,然后通过 Claude 的写入功能修改真实目标。realpath 能识破这种伪装。

❓ 疑惑 6: 什么是符号链接循环(ELOOP)和悬空符号链接?

澄清:

  • 符号链接循环 (ELOOP): a → b, b → a,文件系统解析时无限循环。代码会显式拒绝。
  • 悬空符号链接 (Dangling symlink): a → /path/that/does/not/exist。链接本身存在,但目标不存在。realpath 报错时 lstat 能区分"真不存在"和"链接指向不存在"。
❓ 疑惑 7: findCanonicalGitRoot 是什么?为什么需要?

澄清: Git 支持worktree(一个仓库的多个工作副本)。例如:

main repo:   /home/user/myapp/
worktree:    /home/user/myapp/.claude/worktrees/feature-x/
             ↑ 这也是个 git repo,但它指向同一个 .git 目录

如果 AI 在 worktree 里工作,普通的 git root 会返回 worktree 路径,这意味着每个 worktree 都有独立的 Auto Memory 目录——但用户期望的是同一个项目共享一个记忆空间。

findCanonicalGitRoot() 会解析 worktree 链接,返回主仓库路径。这是为什么代码注释说:"all worktrees of the same repo share one auto-memory directory"。

前端类比: 类似 monorepo 里每个 package 的 package.json 路径解析——你希望子包能找到根目录的共享配置。

❓ 疑惑 8: 什么是 JSONL?

澄清: JSON Lines (jsonlines.org) —— 每行一个合法 JSON 对象的文本格式:

{"role":"user","content":"hello"}
{"role":"assistant","content":"hi"}
{"role":"user","content":"how are you?"}

Claude Code 用 JSONL 存储会话转录日志。原因:

  • 每行独立,可以 grep、tail -f 流式追加
  • 崩溃时只丢失部分行,不会损坏整个文件
  • 天然支持 grep -n 行号定位
❓ 疑惑 9: 什么是 compact 操作?

澄清: compact 是"压缩上下文"的简称。当对话历史太长、超出模型上下文窗口时,Claude Code 会:

  1. 用 LLM 把早期对话总结成简短摘要
  2. 保留最近 N 轮原文
  3. 用摘要 + 最近轮次拼接成新的上下文

这是短期记忆的管理,跟本文档讲的长期记忆(磁盘文件)是两套独立机制。Session Memory 的存在正是为了让 compact 有更结构化的"当前状态"信息可参考。

🟨 类别三:AI / LLM 概念

❓ 疑惑 10: 什么是 "Prompt Cache"?

澄清: 每次调用 LLM API,都需要把所有"输入"重新计算一遍(称为prefill),这部分非常昂贵。Claude API 提供了 prompt cache 功能:如果连续的两次请求有相同的前缀,前缀部分只计算一次,后续请求可以缓存命中。

记忆系统怎么利用: 系统的提示词非常长(几千 token),如果每次用户发消息都重新计算,会非常慢。Claude Code 把"系统提示"做成缓存前缀,后续请求只要前缀不变就命中缓存。

这就是为什么 systemPromptSection('memory', () => loadMemoryPrompt()) 用了缓存包装器——只要记忆内容没变,系统提示前缀就不变,缓存就命中。

前端类比: 类似 React.memo + useMemo——计算结果依赖的"输入"没变,就复用上次的"输出"。

❓ 疑惑 11: 什么是 "Forked Agent"?

澄清: 想象主对话是一个"推理过程"。当主 Agent 完成一轮回复后,系统需要"让它反思一下有没有要记住的事"——但又不想打断用户、不想让主对话的缓存失效。

解决方案是 fork(分叉)出一个一模一样的子代理:

  • 系统提示相同 → prompt cache 命中
  • 对话历史相同 → 模型有同样的"上下文"
  • 但工具权限受限 → 只能做记忆相关操作
  • 并行运行 → 不阻塞主对话

Git 里的 git fork 分支是同个概念:共享基础、独立演进。

❓ 疑惑 12: sideQuery 是什么?

澄清: 与主对话完全隔离的一次性 API 调用。区别:

特性主对话sideQuery
用途与用户交互的完整对话辅助决策的小型查询
消息历史完整只有 prompt 那一两条
成本高(完整上下文)低(只发 prompt)
典型用例回答用户问题分类、判断、抽取等

记忆召回中,系统用 sideQuery 让 Sonnet 一次性挑出最相关的 5 个记忆,而不是在主对话里让模型做这件事——会浪费大量 token。

❓ 疑惑 13: 什么是 Anthropic SDK 的 "Streaming Events"?

澄清: LLM API 支持流式响应(像 ChatGPT 那样边生成边显示)。Anthropic SDK 发送一系列 BetaRawMessageStreamEvent 事件:

  • message_start — 开始
  • content_block_start — 文本/工具调用开始
  • content_block_delta — 增量内容(一个字一个字)
  • content_block_stop — 结束
  • message_stop — 整个消息结束

前端类比: 类似 Server-Sent Events (SSE) 或 WebSocket 的流式消息协议。

❓ 疑惑 14: 为什么"全量加载 CLAUDE.md"在 system prompt 里是好事?

澄清: 看起来很浪费 token,但有两个理由:

  1. 一致性: 每次调用 LLM 看到的指令完全相同 → prompt cache 完美命中,边际成本接近 0
  2. 避免遗忘: LLM 在长对话中容易"丢失"指令(称为 "lost-in-the-middle" 现象),全量塞在 system prompt 中能持续生效

🟩 类别四:状态管理与缓存

❓ 疑惑 15: 什么是 memoize ?为什么 getProjectRoot 作为 key?

澄清: memoize 是函数级别的记忆化(类似 React.useMemo):同样的输入返回缓存的输出,避免重复计算。

// lodash-es 的 memoize 允许指定 key 函数
memoize(
  () => computeExpensiveThing(),
  () => getProjectRoot()  // 用 projectRoot 作为缓存 key
)

为什么用 getProjectRoot() 作为 key: 因为同一个 CLI 进程里,projectRoot 通常不变。如果中途切换了项目(测试场景),key 变化触发重算。

前端类比: 就是 useMemo(() => compute(a, b), [a, b]) 的函数式版本。

❓ 疑惑 16: 什么是 closure-scoped state? 为什么 initExtractMemories() 用闭包?

澄清: 看 extractMemories.ts:296:

// 模块顶层:
let extractor: ((...) => Promise<void>) | null = null

// 初始化时:
export function initExtractMemories() {
  // 这些变量都在这个函数作用域内
  let lastMemoryMessageUuid: string | undefined
  let inProgress = false
  let pendingContext = undefined
  ...

  // 它们被内部函数捕获,形成闭包
  extractor = async (context, ...) => {
    // 这里能访问上面所有变量
  }
}

原因: 多个测试可以调用 initExtractMemories() 各自得到独立的状态副本(因为每次调用都创建新的闭包),不会相互污染。生产环境只调用一次。

前端类比: 类似 React 的 useState——每次组件挂载都有独立状态。

❓ 疑惑 17: 什么是 "System Prompt Section" 注册模式?

澄清: 系统提示很长,分成多个独立可缓存的"section":

systemPromptSection('memory', () => loadMemoryPrompt())
systemPromptSection('language', () => getLanguageSection(...))
systemPromptSection('output_style', () => getOutputStyleSection(...))

每个 section:

  1. 独立缓存(按 name)
  2. 独立失效(改 memory 不会让 language section 也重算)
  3. 按依赖顺序拼接成完整 system prompt

这与 React 的 Context Provider 树形结构类似——每个 provider 独立决定自己的 value。

❓ 疑惑 18: filterInjectedMemoryFiles() 是干什么的?

澄清: 当 feature flag tengu_moth_copse 开启时:

  • Auto Memory 的 MEMORY.md 不注入到 User Context
  • 改用路径 C(按需召回 attachment)注入

原因: 实验性优化——让所有记忆内容都通过 Sonnet 选择后才出现,可能比"先全量塞 MEMORY.md 索引,再召回"更精准。Feature flag 名是 GrowthBook 的实验标识符(moth_copse 是 A/B 测试名)。

🟪 类别五:权限与安全

❓ 疑惑 19: 什么是 DANGEROUS_DIRECTORIES ?

澄清: Claude Code 内置的高风险目录黑名单:

  • ~/.ssh/ — 私钥
  • ~/.aws/ — AWS 凭证
  • ~/.gnupg/ — GPG 密钥
  • ~/.config/ — 各种应用配置

默认情况下,AI 写入这些目录需要显式用户授权。但 isAutoMemPath() 为 true 时会豁免这条规则——因为 auto memory 目录是用户授权的合法位置。

这就是为什么恶意项目设置 autoMemoryDirectory: "~/.ssh" 会被拒绝——只允许从受信的 settings 源(policy/local/user)配置。

❓ 疑惑 20: 什么是 canUseTool 模式?

澄清: Claude Code 的工具调用都要经过 canUseTool 钩子审查:

function canUseTool(tool: Tool, input): { behavior: 'allow' | 'deny', ... }

每个工具调用都先问"我能用这个工具 + 这个输入吗?"。后端提取 Agent 的 canUseTool 非常严格——只允许读类工具和 memory 目录内的写操作。

前端类比: 类似 React 的 useReducer + 中间件,或者类似 Express 的 middleware 链——在"实际执行"前做权限检查。

❓ 疑惑 21: 什么是 "FSM" / 状态机在 inProgress 中的应用?

澄清: 后台提取的状态机:

状态: 空闲 | 执行中 | 暂存待执行

事件流:
空闲 ──新请求──→ 执行中
执行中 ──完成──→ 空闲
执行中 ──新请求──→ 暂存 pendingContext
执行中 ──完成──→ 消费 pendingContext ──→ 执行中(trailing run)
                → 没有 pendingContext → 空闲

这是经典的有"挂起任务"槽位的并发控制模式。

🟥 类别六:前端工程师特有的"语义混淆"

❓ 疑惑 22: "Attachment" 在 Claude Code 里是什么?

澄清: 不是邮件附件,而是一种注入到对话的特殊消息:

  • 类型: attachment
  • 位置: 插入到 user/assistant 消息之间
  • 渲染: 被渲染成 <system-reminder> 包裹的内容

可以理解为 React 中"由框架自动注入的虚拟 DOM 节点"——用户看不见,但模型能感知。

❓ 疑惑 23: <system-reminder> 是什么?前端框架里没这概念啊

澄清: 这是 Anthropic 约定的特殊标签,Claude 看到时会理解成"这是系统提示的一部分,不是用户说的话"。Claude Code 用这个标签来:

  • 在对话中插入"系统级别"的提示
  • 比如记忆召回结果、命令执行结果、文件读取摘要

前端类比: 类似 React DevTools 注入的 __REACT_DEVTOOLS_GLOBAL_HOOK__——不是用户写的,但运行时存在。

❓ 疑惑 24: 什么是 "Hooks" 系统? handleStopHooks、registerPostSamplingHook

澄清: 这是 Claude Code 的生命周期钩子(类似 React 的 useEffect、Vue 的 onMounted):

钩子时机用途
Stop主 Agent 完成一轮回复(无 tool call)触发 extractMemories、autoDream、promptSuggestion
PostToolUse工具调用完成后日志、统计、UI 更新
PostSampling主模型采样后SessionMemory 等后台任务
PreToolUse工具调用前权限检查、输入修改

与 React 的 useEffect 思路相同——在某个时刻自动触发副作用。

❓ 疑惑 25: 什么是 "Tools" (工具) 在 Claude Code 里?

澄清: LLM 不像前端可以"调用任何函数",它只能调用 Claude Code 显式注册的工具。每个工具是一个独立的 module:

  • 有 name、description、inputSchema (Zod schema)
  • 有 call() 函数:实际执行逻辑
  • 有可选的 React 组件:渲染结果到终端

LLM 在对话中通过 tool_use 块调用它们,系统执行后返回 tool_result 块。

前端类比: 类似"自定义 Hooks"——Claude Code 暴露给 LLM 的可调用 API 集合。

❓ 疑惑 26: 什么是 GrowthBook 和那些奇怪的名字(moth_copse、herring_clock)?

澄清: GrowthBook (https://growthbook.io) 是一个开源的 A/B 测试和 Feature Flag 平台。Claude Code 用它做:

  • 灰度发布(只对 5% 用户启用新功能)
  • A/B 测试(对比两种算法的效果)
  • 远程配置(不重新发布就能调整参数)

那些奇怪的名字(tengu_moth_copse、tengu_herring_clock)是实验标识符——每个实验一个唯一名字,方便数据分析时追踪。tengu_ 是项目代码前缀(可能是 "Tengu"——日本佛教中的山神/狐).

前端类比: 类似 LaunchDarkly、Unleash 的 feature key。

❓ 疑惑 27: 什么是 "User Context" 和 "System Context"?

澄清: API 请求被组织成三个独立段:

段位置用途变化频率
System Prompt消息最前行为指令、可用工具偶尔变化
User Context第一条 user messageCLAUDE.md、MEMORY.md、日期每会话变化
System ContextSystem contextgit 状态、运行时信息每次请求

设计意图: 把"很少变"和"经常变"的部分分开,最大化 prompt cache 命中率。

❓ 疑惑 28: 什么是 "Side Query" 的实现细节?

澄清: 调用 LLM 的常规方式是把 prompt 拼到主对话里。但 sideQuery 做的是:

  1. 用 Anthropic SDK 单独发一次 API 请求
  2. 不走 query.ts 主循环
  3. 不走工具调用机制
  4. 只接收文本结果

这是"无状态的一次性 LLM 调用"。类似前端里的 fetch('/api/llm/side', { method: 'POST', body: prompt })——只是 SDK 内部实现。

❓ 疑惑 29: 什么是 readFileState 缓存?

澄清: sessionMemory.ts:216:

// 显式删除缓存,强制下次读文件拿到真内容
toolUseContext.readFileState.delete(memoryPath)

这是 Claude Code 的文件读取缓存层——避免短时间内重复读同一文件。如果不删,SessionMemory 拿到的会是缓存的旧内容。

前端类比: 类似 react-query 的 queryClient.invalidateQueries()——主动让缓存失效,下次重新拉。

❓ 疑惑 30: 那些"KAIROS"、"Tengu" 名字是品牌还是代码?

澄清: KAIROS、Tengu 都是 Anthropic 内部的项目代号。具体含义:

  • Tengu — 整个 Claude Code 项目的代号(山神/天狗)
  • KAIROS — "助手模式"的特性名,源自希腊语"关键时刻"
  • TeamMem — Team Memory 特性

这不是营销品牌,而是内部命名空间——目的是让代码 feature flag 和模块名不与未来可能的商业产品名冲突。
