1. 总览：Skill 系统的定位

Skill 是 Claude Code 中一种可插拔的 prompt 注入机制。它将结构化的 markdown 文档（SKILL.md）在运行时注入到对话上下文中，赋予模型额外的领域知识和行为指引。

从架构角度看，Skill 位于 "用户输入 → 模型推理" 这条链路的中间层：

  • 用户可以通过 /skill-name 手动触发
  • 模型可以通过 SkillTool 自动触发（基于 when_to_use 描述判断）
  • Skill 内容被处理后作为 UserMessage 注入对话，模型据此执行
核心设计理念

Skill 本质上是一种延迟加载的 prompt：平时只以摘要形式列在 system-reminder 中（节省 token），只在被调用时才加载完整内容注入上下文。这避免了所有 skill 内容同时占用宝贵的上下文窗口。

2.1 动态发现（运行时）

源文件：loadSkillsDir.ts:861 — discoverSkillDirsForPaths()

当模型执行 Read/Edit/Write 操作时，系统会沿文件路径向上查找嵌套的 .claude/skills/ 目录，动态加载新 skill。触发点位于三个文件工具中：

// FileReadTool.ts:579
const newSkillDirs = await discoverSkillDirsForPaths([fullFilePath], cwd)
addSkillDirectories(newSkillDirs).catch(() => {})

// FileEditTool.ts:408 和 FileWriteTool.ts:234 中完全相同的模式

具体例子：Monorepo 子项目自带 Skill

假设项目结构如下：

/home/user/my-project/                  ← cwd（启动 Claude Code 的目录）
├── .claude/
│   └── skills/
│       └── review-pr/SKILL.md          ← 启动时已加载（cwd 级别）
├── src/
│   └── main.ts
└── packages/
    └── payment-service/                ← 子项目自带自己的 .claude/skills
        ├── .claude/
        │   └── skills/
        │       └── deploy-payment/
        │           └── SKILL.md        ← 启动时不会被发现！
        └── src/
            └── checkout.ts

启动时 getSkillDirCommands() 从 cwd 向上遍历到 $HOME，它找到了 review-pr，但看不到 deploy-payment——因为 deploy-payment 在 cwd 的子目录里，向上遍历覆盖不到。

运行时，当模型读取 packages/payment-service/src/checkout.ts：

discoverSkillDirsForPaths(["packages/payment-service/src/checkout.ts"], cwd)

① 从文件的 父目录 开始往上走：
   packages/payment-service/src/.claude/skills/  → 不存在

② 再往上一层：
   packages/payment-service/.claude/skills/      → 存在！✅
   → newDirs.push("packages/payment-service/.claude/skills")

③ 继续往上：
   packages/.claude/skills/                     → 不存在

④ 到达 my-project/ (= cwd) → 停止（不含 cwd 本身）

随后 addSkillDirectories() 加载 deploy-payment/SKILL.md，该 skill 现在可用了。

安全保护

机制说明
cwd 是上界 只向上走到 cwd（不含），cwd 级别的 skill 已在启动时加载，避免重复
gitignore 检查 被 gitignore 的目录无条件跳过，防止 node_modules/some-pkg/.claude/skills/ 被偷偷加载
去重缓存 dynamicSkillDirs（Set）记录已检查过的目录，同一目录只检查一次
深度优先覆盖 路径更深的 skill 优先，靠近文件的 skill 覆盖上层同名 skill
设计意图

这个机制让 Monorepo 的子包可以携带自己的 skill，只有当模型真正接触到那个子包的代码时 skill 才被激活——避免了启动时加载整个代码库所有子目录的 skill。

2.2 条件激活

源文件：loadSkillsDir.ts:997 — activateConditionalSkillsForPaths()

与 2.1 动态发现的区别

动态发现 (2.1)：在运行时找到新的 .claude/skills/ 目录并加载。
条件激活 (2.2)：skill 已在启动时加载（目录在 cwd 或被向上遍历到），但处于休眠态，只有模型触及匹配文件时才激活（展示给模型）。

工作流程

带 paths: frontmatter 的 skill 在启动时被解析，但不会被立即返回给模型。它们被存入 conditionalSkills Map：

// loadSkillsDir.ts:771-800（getSkillDirCommands 中）
for (const skill of deduplicatedSkills) {
  if (skill.paths && skill.paths.length > 0 && !activatedConditionalSkillNames.has(skill.name)) {
    newConditionalSkills.push(skill)   // → 存入休眠池
  } else {
    unconditionalSkills.push(skill)    // → 直接返回给模型
  }
}
// 休眠池：conditionalSkills.set(skill.name, skill)
return unconditionalSkills  // 模型暂时看不到条件 skill

当模型通过 Read/Edit/Write 触及文件时，系统检查路径是否匹配：

// activateConditionalSkillsForPaths() 的核心逻辑
for (const [name, skill] of conditionalSkills) {
  const skillIgnore = ignore().add(skill.paths)
  for (const filePath of filePaths) {
    if (skillIgnore.ignores(relativePath)) {
      dynamicSkills.set(name, skill)     // → 激活！
      conditionalSkills.delete(name)      // → 移出休眠池
      activatedConditionalSkillNames.add(name)
      break
    }
  }
}

# .claude/skills/database-migration/SKILL.md
---

场景行为
启动时 skill 被加载解析，但不展示给模型（进入 conditionalSkills 休眠池）
模型 Read src/utils/helper.ts 不激活 — 路径不匹配 migrations/** 或 db/schema/**
模型 Edit migrations/2026_add_users.sql 激活！✅ — 匹配 migrations/**，skill 立刻变为可用
模型 Write db/schema/users.ts 激活！✅ — 匹配 db/schema/**

匹配规则

  • 使用 ignore 库，完整 gitignore 语义（*、**、! 取反等）
  • paths 接受逗号分隔字符串或 YAML 数组
  • 支持花括号展开：paths: "src/*.{ts,tsx}" → src/*.ts + src/*.tsx
  • 所有模式都是 ** 时视为无条件（不进入休眠池）
  • 匹配基于文件相对于 cwd 的路径，绝对路径自动转换
  • 激活后该 skill 名称记录到 activatedConditionalSkillNames，即使缓存清空也不会再休眠

2.3 去重

通过 realpath() 解析符号链接，确保同一个物理文件只被加载一次（line 118-124）。先加载的优先。

4. 注册阶段：统一的 Command 对象

源文件：loadSkillsDir.ts:270 — createSkillCommand()

所有来源的 skill 最终被构造为统一的 Command 对象（type: 'prompt'），其核心是一个闭包函数 getPromptForCommand(args, context)：

async getPromptForCommand(args, toolUseContext) {
  // Step 1: 添加 Base Directory 前缀
  let finalContent = baseDir
    ? `Base directory for this skill: ${baseDir}\n\n${markdownContent}`
    : markdownContent

  // Step 2: 参数替换 $ARG_NAME → 实际值
  finalContent = substituteArguments(finalContent, args, true, argumentNames)

  // Step 3: 变量替换 ${CLAUDE_SKILL_DIR} → skill 目录路径
  if (baseDir) {
    finalContent = finalContent.replace(/\$\{CLAUDE_SKILL_DIR\}/g, skillDir)
  }

  // Step 4: 变量替换 ${CLAUDE_SESSION_ID} → 当前会话 ID
  finalContent = finalContent.replace(/\$\{CLAUDE_SESSION_ID\}/g, getSessionId())

  // Step 5: 内联 shell 命令执行 !`cmd` 和 ```! cmd ```
  if (loadedFrom !== 'mcp') {  // MCP skill 出于安全考虑不执行
    finalContent = await executeShellCommandsInPrompt(finalContent, ...)
  }

  return [{ type: 'text', text: finalContent }]
}
关键设计：延迟内容加载

getPromptForCommand 是一个闭包，捕获了 markdownContent、baseDir、argumentNames 等变量。完整内容只在 skill 被调用时才处理，而不是在加载阶段。这实现了按需加载。

Bundled skill 使用 registerBundledSkill(definition) 注册，支持额外的 files: 属性，将参考文件提取到磁盘：

5.1 Token 预算控制

  • 总预算 = 上下文窗口的 1%（约 8000 字符 / 200k 窗口）
  • 每条描述硬上限 250 字符（MAX_LISTING_DESC_CHARS）
  • Bundled skill 的描述永不截断
  • 超预算时：先等比截断非 bundled 描述，极端情况下只显示名称

5.2 展示格式

- gitnexus-exploring: Use when the user asks how code works... - "How does X work?", "What calls this function?"
- gitnexus-impact-analysis: Use when the user wants to know what will break... - "Is it safe to change X?"
- teach-me: Personalized 1-on-1 AI tutor... - Use when user wants to learn/study/understand a topic

7. 内容处理阶段：Skill 正文的变量替换与 Shell 执行

7.1 内联 Shell 执行细节

源文件：src/utils/promptShellExecution.ts

支持两种语法：

语法示例说明
内联 !`git branch --show-current` 适合简短命令，输出替换到原位置
代码块 ```! tree -L 2 ``` 适合多行命令，支持管道

执行过程：

  1. 正则匹配 BLOCK_PATTERN 和 INLINE_PATTERN
  2. 通过 BashTool 的权限检查流程
  3. 调用 BashTool.call({ command }) 实际执行
  4. 将输出替换回原位置（String.replace 使用函数 replacer 防止特殊字符破坏）
安全限制

MCP 来源的 skill（loadedFrom === 'mcp'）不会执行内联 shell 命令。MCP skill 被视为远程且不受信任的内容。

7.2 Shell 类型选择

通过 frontmatter shell: 字段指定：

  • bash（默认）→ 使用 BashTool
  • powershell → 使用 PowerShellTool（仅在启用时可用，惰性加载）

8. 其他文件的引用机制（核心）

这是 skill 系统中最关键的设计之一——skill 正文中如何引用和使用其他文件。共有五种机制：

机制 1：${CLAUDE_SKILL_DIR} 路径变量 最常用

SKILL.md 正文中使用 ${CLAUDE_SKILL_DIR} 变量引用 skill 目录下的文件：

# SKILL.md 中写道：
Read ${CLAUDE_SKILL_DIR}/references/pedagogy.md for teaching methodology.
See ${CLAUDE_SKILL_DIR}/examples/advanced.md for advanced examples.

在 getPromptForCommand 闭包中，${CLAUDE_SKILL_DIR} 被替换为 skill 目录的绝对路径。

重要：这不是自动包含

${CLAUDE_SKILL_DIR} 只是路径替换，不会自动读取文件内容。它告诉模型文件在哪里，模型自己决定是否使用 Read 工具去读取。这是一种间接引用。

机制 2：@-mention 文件附件自动加载 自动包含

源文件：processSlashCommand.tsx:1222

如果 SKILL.md 内容中包含 @filename 的引用，getAttachmentMessages() 会自动解析并将文件内容作为 attachment message 注入到对话中。

# SKILL.md 中写道：
参考 @config.json 了解配置结构。

处理过程：

const attachmentMessages = await toArray(
  getAttachmentMessages(
    result.filter(b => b.type === 'text').map(b => b.text).join(' '),
    context, null, [], context.messages, 'repl_main_thread',
    { skipSkillDiscovery: true },  // 防止大文件触发 AKI 查询
  ),
)
唯一的"自动包含"机制

@-mention 是唯一一种文件内容会被自动读取并注入到上下文中的机制。其他机制都只是提供路径，由模型自行决定读取。

机制 3：内联 Shell 命令（动态内容生成）动态

通过 !`cmd` 语法在加载时动态执行命令，将输出注入到 skill 内容中：

# SKILL.md 中写道：
当前工作目录的 git 分支是 !`git branch --show-current`
项目结构：
```!
tree -L 2 src/
```

命令输出会替换原始语法，适合注入运行时动态信息。

机制 4：Bundled Skill 的 files: 磁盘提取 仅 Bundled

源文件：bundledSkills.ts:131

Bundled skill 通过 files: 字段将参考文件提取到磁盘临时目录，模型可以按需 Read：

registerBundledSkill({
  name: 'verify',
  files: {
    'examples/cli.md': cliMdContent,
    'examples/server.md': serverMdContent
  },
  getPromptForCommand(args) { ... }
})

安全措施：

  • 写入路径包含 per-process nonce，防止预创建攻击
  • 文件权限 0o600，目录权限 0o700
  • 使用 O_NOFOLLOW + O_EXCL 防止符号链接攻击
  • 路径遍历检查（禁止 ..）

9.1 内容特征

9.2 引用方式

GitNexus skill 的引用完全依赖 CLAUDE.md 的间接引导：

# CLAUDE.md 中的相关段落：
## Always Do
- MUST run impact analysis before editing any symbol.
  Run `gitnexus_impact(...)`

## CLI
| Task | Read this skill file |
|------|---------------------|
| "How does X work?" | `.claude/skills/gitnexus/gitnexus-exploring/SKILL.md` |
| "What breaks if I change X?" | `.claude/skills/gitnexus/gitnexus-impact-analysis/SKILL.md` |

工作流：

  1. CLAUDE.md 作为上下文注入到 system prompt
  2. CLAUDE.md 中的表格指向具体的 skill 文件路径
  3. 模型看到后，主动使用 Read 工具读取对应的 SKILL.md
  4. 读取到的 skill 内容指导模型使用 GitNexus MCP 工具
为什么不使用 Skill 系统的标准引用机制？

GitNexus skill 的设计选择了最简单的方式——纯 markdown 指南文档。它们不需要引用其他文件（没有 references/ 子目录），不需要动态内容（没有 shell 命令），也不授权额外工具。这种设计是合理的：skill 本身就是 MCP 工具的使用手册。
