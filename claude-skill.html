01概述

Skill 是 Claude Code 中以目录形式组织的可复用指令包。每一个 skill 的核心是一个 SKILL.md 文件，其中包含 YAML frontmatter（控制 skill 的元行为）和 markdown 正文 （要注入到模型上下文的指令）。系统启动时从五个来源扫描、解析、注册所有 skill；当模型或用户触发时， Skill 工具把整个 SKILL.md 正文作为 <system-reminder> 包裹的 user 消息注入到当前对话。

两种调用入口

  • 用户输入 /skill-name — REPL 检测斜杠前缀，调用 processSlashCommand，最终进入 getMessagesForPromptSlashCommand。
  • 模型自主调用 Skill 工具 — 流式响应解析出 tool_use 块后，由 runTools 派发到 SkillTool.call，最终在动态 import 之后 复用到 processPromptSlashCommand 这一条路径。
💡两条路径在执行层会聚：模型调用 Skill 工具时，会通过动态 import('src/utils/processUserInput/processSlashCommand.js') 复用斜杠命令的处理函数。SkillTool 只是"鉴权 + 内嵌模式选择 + newMessages 注入" 的薄包装。

三种执行上下文

模式触发条件行为
inline（默认） 无 frontmatter 或 context: inline 把 SKILL.md 正文作为 isMeta: true user 消息注入到当前对话
fork context: fork 在隔离的子 agent 中执行（默认 general-purpose），子 agent 的最终文本作为 tool_result 返回
remote canonical _canonical_<slug> 命名空间 + EXPERIMENTAL_SKILL_SEARCH 从 AKI / GCS / S3 拉取 SKILL.md，内联注入；仅 ant build 生效
💡 补充说明 ESSENCE 第 1 节扩展 · Skill 的本质

剥到最底层，模型看到的就是一条 user-role 消息里塞的 SKILL.md 正文。 在这个意义上，skill 就是一个预先组织好的 prompt。 但如果只看到这一点，会漏掉 skill 真正解决的问题。下面分三层来理解它"是什么"。

三个层面看"Skill 是什么"

视角本质类比
对模型 一条 user 消息里塞的指令（<system-reminder> 标签只是让 Claude 当作系统级指令处理） 机器码
对开发者 一个声明式的 manifest：YAML frontmatter + markdown 正文的组合 带 package.json 的代码
对运维 一套来源优先级 + 权限边界 + 生命周期管理的子系统 带 manifest 的 Docker 镜像

如果不用 skill 系统，自己实现需要写什么？

用底层 API 直接拼 prompt，你需要自己处理：

  1. 前缀拼装（base directory 头、$ARGUMENTS 替换）
  2. inline shell 命令（!`cmd`）执行与结果内联
  3. permission 检查（deny / allow / ask 三态机）
  4. tool_use 之后 newMessages 的构造与时序
  5. compaction 后如何让 skill 内容复活
  6. 对模型隐藏"系统级注入"，避免污染用户 UI

Skill 工具把这六件事都替你做了，开发者只写一份带 frontmatter 的 markdown。

一句话定义：Skill 是一个声明式的"prompt 配方 + 运行时容器"—— 开发者只写一份带 frontmatter 的 markdown，运行时（CLI）负责发现、解析、权限、注入、生命周期、跨上下文复活。

为什么是 system-reminder 而不是 system prompt？

把 skill 列表放成 isMeta: true 的 user 消息有几个隐含好处：

  • resume 会话时增量注入新发现的 skill（suppressNext 机制）
  • 动态 skill 出现在会话中时能立即生效（getDynamicSkills() 追加）
  • 不污染系统提示的 cache key（系统提示的 prompt cache 命中率高，频繁改列表会击穿）
  • UI 隐藏（isMeta），用户看不见这条"声明"
🔍 补充说明 NAMING 第 5 节扩展 · 消息机制澄清

本节涉及两个容易混淆的命名：<system-reminder> 标签和 isMeta: true 字段。 名字里都带"system"或暗示"系统"，但实际机制与字面意思有差距。下面分别澄清。

澄清 1 · <system-reminder> 是 role: "user" 消息

"system" 这个词指的是XML 标签名，不是消息 role。 实际发到 API 的结构是： 

{
  "role": "user",                              ← 是 user，不是 system
  "content": [
    {
      "type": "text",
      "text": "<system-reminder>\nThe following skills are available...\n</system-reminder>"
    }
  ]
}

代码证据：

// messages.ts:3764-3774
case 'skill_listing': {
  return wrapMessagesInSystemReminder([
    createUserMessage({                        // ← createUserMessage, 不是 createSystemMessage
      content: `The following skills are available for use with the Skill tool:\n\n${attachment.content}`,
      isMeta: true,
    }),
  ])
}

createUserMessage 生成的 API 消息 role 是 "user"。 API 消息层没有任何 system 角色消息，所有"系统提示"实际都是 system prompt 里的固定字符串（role: "system"，由 context.ts 构建） + 这类 user-role 的"伪 system"消息。

为什么这么设计？

  • <system-reminder> 是 Anthropic 在 prompt 里约定的 XML 语法， Claude 被训练成"看到此标签就当作系统级指令"——但 API 没有为这种"动态系统级提示"专门开 role，就用 user + XML 标签模拟
  • 真 system prompt 固定（context.ts 拼一次），适合 prompt cache； skill 列表和 body 每个 turn 都在变，做成 user-role 消息可以独立注入而不污染 system prompt 的 cache key
  • isMeta: true（见下）控制 UI 显隐

澄清 2 · isMeta: true 的三作用

isMeta 是 Message 类型上的 boolean 字段 （定义在 src/types/message.ts），影响三处：

  1. UI 不渲染（用户看不见）—— 渲染层过滤掉 isMeta: true 的消息。 这就是为什么 skill 列表、permission 提示、inline skill body 这些"系统级噪声"不会污染对话流。
  2. API role 仍是 user——isMeta 不改变消息 role。这与"system-reminder 是用户消息"的事实一致。 isMeta 只影响 Claude Code 这边的 UI 层。
  3. 序列化/持久化区别对待——转 JSONL 存盘（transcript）和 resume 时， isMeta 标记通常被保留，但有些 case 会被剥离。 代码在 src/utils/messages.ts 的 toMessageForLLM / serializeMessage 系列函数里。

三个"系统提示"层级对比

来源消息 role频率是否走 cache
真正的 system prompt "system" 整个会话一次 ✅ 高命中
skill 列表 system-reminder "user"（XML 标签） 每个 turn ⚠️ 视实现
skill body system-reminder "user"（XML 标签） 调用时一次 ⚠️ 视实现
<command-name> / <command-message> "user" 调用时 ❌

XML 标签 vs isMeta：两个独立机制

注意区分两个概念：

  • <system-reminder>…</system-reminder> 是文本内容里的 XML 标签
  • isMeta: true 是消息对象上的 boolean 字段

两者经常同时出现（如 skill 列表），但概念独立：

✅ 有✅ true标准"系统级消息"模式：模型当指令，UI 隐藏
❌ 无✅ trueUI 隐藏，但模型当成普通用户消息
✅ 有❌ falseUI 显示这条"系统提示"，模型当指令
❌ 无❌ false普通用户消息

命名总结：<system-reminder> 是文本标签（给模型看）， isMeta: true 是消息标记（给 UI 看）， 两者各管一摊，名字里都有"system"纯属巧合。

本节上方覆盖了 inline 模式完整调用链。下面是对其中三个关键设计点的进一步展开， 以及三种执行模式的"注入位置"对比。这些细节未在主章节单独成块，列在此处便于查阅。

关键点 1 · 三个语义位点各司其职

一个 inline skill 调用实际上由三段连续消息组成，承担不同角色：

位点类型实际内容来源
1 <tool_use> 块 {name: "Skill", input: {skill: "commit", args: ""}} 模型在 assistant turn 里发出
2 <tool_result> 块 "Launching skill: commit"（仅这一行） SkillTool.ts:861 mapToolResultToToolResultBlockParam
3 user 消息 isMeta: true 完整 SKILL.md 正文（base-dir 头 / $ARGUMENTS 替换 / inline shell 已执行） processSlashCommand.tsx:1242-1245

这种"三段式"设计的隐含好处：tool_result 简洁、机器可读； skill 正文作为"自然语言指令"自然地进入对话流； 配合 <command-name> 标签防止模型再次调用同一个 skill （避免 issue #59363 报告的冗余 invoke 错误）。

关键点 2 · isMeta: true 与 <system-reminder> 包裹

isMeta 标记让 UI 隐藏这条 user 消息（用户看不到）， 但模型能看到。配合 wrapMessagesInSystemReminder， 最终转给 API 的 JSON 长这样： 

{
  "role": "user",
  "content": [
    {
      "type": "text",
      "text": "<system-reminder>\nThe following skill has been loaded:\n\n<command-name>/commit</command-name>\n<command-message>commit</command-message>\n\n[完整 SKILL.md 正文]\n</system-reminder>"
    }
  ]
}

与 skill 列表（messages.ts:3764-3774）的 case 'skill_listing' 用的是同一套包裹函数——列表是"有哪些 skill 可用"， inline 注入是"现在用这个 skill"，在 Anthropic 的设计里都视为"系统级元信息"。

关键点 3 · contextModifier 才是 inline 真正的副作用

SkillTool.ts:776-840 的 contextModifier 在 skill 调用之后修改主循环的状态。这是 inline 模式独有的——fork 模式下 这些都进子 agent，不会污染主循环。 

contextModifier(ctx) {
  // ① allowed-tools 注入主循环的 permission context
  if (allowedTools) {
    getAppState().toolPermissionContext
      .alwaysAllowRules.command.push(...)
  }
  // ② 切换主模型；'inherit' 表示跟随当前，保留 [1m] 后缀（防 compact 切错模型）
  if (model) {
    resolveSkillModelOverride(model, ctx.options.mainLoopModel)
  }
  // ③ 设置推理 effort
  if (command.effort !== undefined) {
    appState.effortValue = effort
  }
}

也就是说，inline skill 调用实际上在主循环里做了三件副作用： 给当前用户静默授权、切换模型、改 effort。这与 fork 模式"隔离副作用"形成对照。

三种执行模式的"注入位置"对比

模式 body 出现在哪 tool_result 返回 主对话是否受影响
inline（默认） 主对话的 newMessages（user 消息） "Launching skill: <name>" ✅ 是（模型 / 工具 / effort 都可能变）
fork 子 agent 的初始 prompt Skill "<name>" completed (forked execution).\n\nResult: <result> ❌ 否（除非显式声明）
remote canonical 主对话的 newMessages（user 消息） "Launching skill: <name>" ✅ 是（仅 ant build）

一句话总结：Inline 模式 = "把 SKILL.md 的全文直接喂给主对话里的模型，让它接着执行"。 与 fork 的"派个 sub-agent 去跑"刚好相反。

10为什么这么设计

设计动机分两层：1) Anthropic 公开的设计原则；2) GitHub issue 反映的为什么这么实现而非其他方式。

10.1 Progressive Disclosure（官方反复强调的核心原则）

Anthropic 工程博客（anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills）原文：

📖 EN Original ⇄ ZH 译文
"This metadata is the first level of progressive disclosure: it provides just enough information for Claude to know when each skill should be used without loading all of it into context."
"这些元数据是渐进式披露（progressive disclosure）的第一层：它为 Claude 提供了足够的信息，使其知道何时应该使用每个 skill，而无需将所有内容加载到上下文中。"
— Anthropic Engineering Blog
📖 EN Original ⇄ ZH 译文
"Progressive disclosure is the core design principle that makes Agent Skills flexible and scalable. Like a well-organized manual that starts with a table of contents, then specific chapters, and finally a detailed appendix, skills let Claude load information only as needed."
"渐进式披露是让 Agent Skills 兼具灵活性与可扩展性的核心设计原则。就像一本组织良好的手册——从目录开始，再到具体章节，最后是详细附录——skill 让 Claude 能够按需加载信息。"
— Anthropic Engineering Blog

开放规范 agentskills.io 把这个模型正式化为三阶段：

  1. Discovery — 启动时 agent 只加载每个 skill 的 name + description，足以知道何时可能相关
  2. Activation — 任务匹配时，agent 读取完整 SKILL.md 指令进入上下文
  3. Execution — agent 遵循指令，可选地执行捆绑代码或加载引用文件

官方支持文档：

📖 EN Original ⇄ ZH 译文
"Skills work through progressive disclosure—Claude determines which skills are relevant and loads the information it needs to complete that task, helping to prevent context window overload."
"Skill 通过渐进式披露机制工作——Claude 判断哪些 skill 是相关的，并加载完成任务所需的信息，这有助于避免上下文窗口过载。"
— support.claude.com/en/articles/12512176

10.2 当前实现 vs 官方承诺的落差

⚠️反编译代码的实际行为只做到了阶段 1（listing 截断）和阶段 3（执行），阶段 2 的"按需加载正文"在 Claude Code 里没有实现—— 所有 SKILL.md 在启动时就被 fs.readFile 读进内存，body 已在闭包里。 模型不会感知"我是先看了 metadata 才加载 body"的两步过程。这与官方叙事有差距。

10.3 为什么选 YAML frontmatter？

从 issue #56448 用户的发现（2026-05-27）来看： skillListingBudgetFraction（默认 0.01）和 skillListingMaxDescChars（默认 1536） 这两个 budget 配置是打包在 Zod schema 里的，但未在公开文档。这暗示：

  • Anthropic 在 schema 层做了中央化，避免每个 skill 作者各自魔改边界
  • YAML frontmatter 是 OpenSSF 生态的事实标准（GitHub Pages、Hugo、Zola、Eleventy 等都用），社区认知成本低
  • 支持跨产品（Claude Code / Claude apps / OpenAI Codex / Cursor / GitHub Copilot 等 ~30 个产品采纳 Agent Skills 规范）

10.4 为什么把列表放进 system-reminder 而不是 system prompt？

从反编译代码可以反推几个考量：

  • Resume 友好：恢复会话时增量注入新 skill（suppressNext 机制）
  • 动态 skill 即时生效：getDynamicSkills() 追加
  • 保护 prompt cache：系统提示的 cache key 不变；列表变更只击穿 user 消息层
  • UI 隐藏：isMeta: true 让用户看不到"系统广告"

10.5 为什么 SKILL.md 引用是"裸"的（不预加载）？

这反映了 prompt injection 威胁模型——引自 Anthropic 工程博客：

📖 EN Original ⇄ ZH 译文
"Skills provide Claude with new capabilities through instructions and code. While this makes them powerful, it also means that malicious skills may introduce vulnerabilities in the environment where they're used or direct Claude to exfiltrate data and take unintended actions. We recommend installing skills only from trusted sources."
"Skill 通过指令和代码为 Claude 提供新的能力。虽然这让它们非常强大，但也意味着恶意 skill 可能会在使用环境中引入漏洞，或指挥 Claude 窃取数据、执行非预期操作。我们建议仅从可信来源安装 skill。"
— Anthropic Engineering Blog

主要威胁：prompt injection 和 data exfiltration。 因此"系统不预先解析、不自动 include 兄弟文件"是一个安全边界的最小化原则—— 让所有文件访问都走 Read 工具（受通用权限系统约束），避免 skill 作者偷偷 include 大文件绕过 review。

MCP skill 完全禁用 inline shell（loadSkillsDir.ts:371-374）也是同一原则的体现： 远程/不可信源 → 拒绝执行任何代码块。

10.6 Trust unit 模型（issue #59366 提案）

2026-06-02 的 issue #59366 提出"skill-scoped permissions"，社区共识是 skill 应该作为信任单元：

📖 EN Original ⇄ ZH 译文
"Skills already declare their identity, purpose, and invocation instructions in that file — permissions_required would fit naturally there. When a user explicitly invokes /skill-name, they've already expressed trust in that skill; requiring them to also manually expand a global pattern list is redundant and undermines the 'skills as units of trust' mental model."
"Skill 已经在文件中声明了它的身份、用途和调用指令——permissions_required 字段放在那里会非常自然。当用户显式调用 /skill-name 时，他们已经表达了对该 skill 的信任；还要求他们手动扩展一个全局 pattern 列表是多余的，破坏了 'skill 作为信任单元' 的心智模型。"
— anthropics/claude-code#59366

10.8 跨产品"开放标准"策略

Anthropic 把 Agent Skills 格式作为开放标准发布（agentskills.io）， 列出 ~30 个采纳者：Claude Code、Claude (apps)、OpenAI Codex、Cursor、GitHub Copilot、VS Code、JetBrains Junie、 Gemini CLI、OpenCode、OpenHands、Mux、Amp、Letta、Firebender、Goose、Factory、Spring AI、Roo Code、Kiro、Emdash、Tabnine 等。

这意味着 YAML + SKILL.md 是一种跨厂商兼容层——你的 skill 在 Claude Code 写出来，可以移植到 Cursor 或 OpenCode。这种开放策略是 OpenAI 的 AGENTS.md / .agents/skills/ 路径未在 Claude Code 原生支持的间接原因（issue #31005、 #56193、#16345、#14836）。
