执行摘要（Executive Summary）

AI Coding Agent 的"记忆"本质上是一组不同 scope（作用范围）、不同生命周期、不同写入方的文件，每个文件对应 LLM 上下文窗口（context window，即模型一次能"看见"的文字长度）之外的一类持久化机制（persistence）。我们研究了三类共 8 个代表系统（Claude Code、Cline、Cursor、Aider、Continue、Roo Code、GitHub Copilot、AGENTS.md 开放标准）以及 Claude Code 2.1.888 自身源码，得出如下结论：

  • 业界已收敛到一个 6 层模型（从最外到最内）：
  • L0 Hook / 强制策略（系统级，不可被 agent 自由忽略）
  • L1 团队/组织级（managed policy，即"组织级托管策略"，所有人强制加载）
  • L2 用户级（个人偏好，跨项目生效）
  • L3 项目级（commit 进仓库的团队公约）
  • L4 子目录 / 路径作用域（按 glob 触发，glob 即"路径通配模式"，按需加载）
  • L5 自动记忆（auto memory，agent 自己写自己的学习笔记）
  • L6 会话内（Plan / Tasks / daily log / transcript）
  • 每一层都有"应写什么"和"应排除什么"两类清单。最关键的边界是：能由 git log / 当前代码 / 文档推导出来的内容都不要写进记忆——这正是 Claude Code 内部 WHAT_NOT_TO_SAVE_SECTION（src/memdir/memoryTypes.ts:183-195）反复强调的反模式。
  • 四类记忆类型（user / feedback / project / reference）已成为共识。Claude Code 用 frontmatter type 字段强制标注，AGENTS.md / Cline / Cursor 都不强制，但写明 type 能让"是否过时"更容易被审计。
  • "索引 + 主题文件"是默认组织模式：MEMORY.md 永远全量加载（被行/字节双重容量限制截断，英文叫 dual cap），具体内容在分散的 *.md 主题文件中。Claude Code 双重限制为 200 行 / 25KB（索引文件本身），Cursor 推荐 500 行以内，社区共识是"Boris Cherny 建议 ~100 行，超过 500 行基本失控"。
  • 三种典型失败模式：
  • Drift（记忆腐化）—— 文件名/函数名还在但实际代码已改；解药是 MEMORY_DRIFT_CAVEAT + 引用前 grep 验证。
  • 过度膨胀 —— 文件越长，agent 越不遵守；解药是按需加载（path-scoped rules / skills）。
  • scope 错位 —— 把团队公约写进个人记忆，反之亦然；解药是 frontmatter 显式声明 scope: private|team。
  • 跨框架互通正在标准化：AGENTS.md 作为 Linux Foundation 旗下 Agentic AI Foundation 的开放格式，Claude Code / Codex / Cursor / Windsurf / Copilot / Aider / Devin / Amp 都已原生支持；不原生支持时用 ln -s AGENTS.md CLAUDE.md 桥接（agents.md FAQ）。
  • Claude Code 2.1.888 的实现是当前最严谨的：4 类记忆（user 用户 / feedback 反馈 / project 项目 / reference 参考）+ 双目录（个人 / 团队） + 双重容量限制（dual cap） + 智能检索（Sonnet selector） + 防腐化机制（drift caveat，防"记忆腐化"）+ 新鲜度警告（freshness warning）——值得在自建系统时直接照搬或精简。

1. 引言：研究范围、方法论与假设

1.1 为什么这个问题值得研究

过去 18 个月，AI Coding Agent 工具链爆炸（Claude Code、Cursor、Cline、Continue、Aider、Roo Code、Copilot Coding Agent、Codex CLI、Devin、Windsurf、Zed AI……）。每个工具都有自己的"instructions 入口"：CLAUDE.md、.cursorrules、.clinerules、AGENTS.md、.windsurfrules、copilot-instructions.md、.continue/rules/、.roo/rules/。

混乱的副作用是：

  • 写在哪里最合适？ 同一个项目可能同时有 CLAUDE.md + .cursorrules + AGENTS.md。
  • 该写什么？ 把整个 README 复制进去？只写 build 命令？还是写"我们团队禁止 X"？
  • 怎么避免记忆腐化？ 上周记的"我们用 pnpm"，这周有人改回 npm。
  • 什么该让 agent 自己记？ 什么该人来写？

本报告把业界实践抽象成 6 层模型，并对每层给出"应写 / 不写 / 何时写"的三段式建议。

1.3 关键假设（显式声明）

  • 受众假设：本报告读者是 AI 工程师 / 团队 lead / 工具作者，他们要么在使用这些工具，要么在为自己的 agent 设计类似的系统。
  • 技术栈假设：默认基于 VSCode-类 IDE / CLI 类工具，浏览器内 IDE（Replit、Bolt）和 Slack/Discord Bot 类 agent 的"记忆"机制略有不同，本报告不覆盖。
  • 时间假设：所有 2026 年以前的内容视为"行业共识"，2026 年新材料（Claude Code 2.1.888、Cursor .mdc 格式、AGENTS.md 进 Linux Foundation）作为"前沿"标注。
  • 范围假设：聚焦文件型记忆（CLAUDE.md / AGENTS.md / .cursorrules 等），不深入 RAG / 向量记忆 / MemGPT 类结构化记忆系统。
  • 价值判断假设：本报告不认可"agent 应该完全自动学习"——大量实战证据表明，没有人类守门人的自动记忆会迅速被 noise 淹没；本报告主张"分层 + 显式标注 + 周期性 prune"。

2. 6 层模型：分层记忆的完整图景

┌────────────────────────────────────────────────────────────────┐
│  L0  Hook / 强制策略         不可被 agent 忽略                 │
│      (PreToolUse hook 钩子, settings, sandbox 沙箱, permissions.deny)         │
├────────────────────────────────────────────────────────────────┤
│  L1  团队/组织级             全员强制                           │
│      (managed policy CLAUDE.md / org copilot-instructions)    │
├────────────────────────────────────────────────────────────────┤
│  L2  用户级                  跨项目生效，仅本机                 │
│      (~/.claude/CLAUDE.md, ~/.claude/rules/, Cursor User Rules)│
├────────────────────────────────────────────────────────────────┤
│  L3  项目级                  团队共享，commit 进仓库            │
│      (./CLAUDE.md, ./AGENTS.md, .cursorrules, .clinerules)     │
├────────────────────────────────────────────────────────────────┤
│  L4  子目录 / 路径作用域      按 glob（路径通配）触发，按需加载             │
│      (.claude/rules/*.md, .cursor/rules/*.mdc, 嵌套 AGENTS.md) │
├────────────────────────────────────────────────────────────────┤
│  L5  自动记忆 (auto memory)   agent 写给自己的笔记               │
│      (~/.claude/projects/<proj>/memory/MEMORY.md + 主题文件)   │
├────────────────────────────────────────────────────────────────┤
│  L6  会话内                  仅当前对话/项目周期有效            │
│      (Plan, Tasks, transcript, daily logs, /dream 蒸馏)        │
└────────────────────────────────────────────────────────────────┘
       ↑ 越往上越强制、越跨 scope
       ↑ 越往下越动态、越依赖 LLM 判断
这 6 层对应到 4 类记忆（user 用户 / feedback 反馈 / project 项目 / reference 参考）时，反馈（feedback）和参考（reference）主要落在 L1/L2/L3；项目（project）落在 L3/L4；用户（user）落在 L2。L5 自动记忆的"type" 字段是这套分类的承载。

3. 每层详解

3.1 L0 · Hook / 强制策略（系统级）

位置：客户端配置 / SDK hook，不是用户可编辑的 markdown。

作用：无论 agent 怎么想，必须执行的硬约束。例：

  • Claude Code 的 PreToolUse hook（钩子）：在 Edit 工具调用前 shell 脚本检查
  • permissions.deny 黑名单：禁止某些命令/路径
  • sandbox.enabled：沙箱（sandbox）隔离

应包含：硬性安全策略、必须执行的命令、不可绕过的合规检查。

应排除：任何"建议"或"指南"——这是 L1-L3 的工作。

典型反模式：把"我们团队禁止用 lodash"写进 permissions.deny——这是 L3 的内容。

关键引用：

"To block an action regardless of what Claude decides, use a PreToolUse hook instead. The more specific and concise your instructions, the more consistently Claude follows them." — Claude Code Memory 文档 译文： 要阻止某个动作（无论 Claude 怎么决定），请改用 PreToolUse hook。指令越具体、越简洁，Claude 遵守得越稳定。

3.2 L1 · 团队/组织级（Managed Policy）

位置：

系统路径
Claude CodemacOS /Library/Application Support/ClaudeCode/CLAUDE.md、Linux /etc/claude-code/CLAUDE.md、Win C:\Program Files\ClaudeCode\CLAUDE.md
GitHub CopilotOrg-level policies via admin console（无文件）
CursorTeam-level rules（在 Cursor Settings 中）

作用：IT/DevOps 部署的硬性公司规范。任何用户都无法 exclude（code.claude.com/docs/en/memory："Managed policy CLAUDE.md files cannot be excluded. This ensures organization-wide instructions always apply regardless of individual settings."；译文：由组织统一部署的 CLAUDE.md 文件不可被排除。这确保组织级指令始终生效，不受个人设置影响。）。

应包含：

  • 公司编码规范（命名、缩进、安全规则）
  • 合规要求（GDPR、SOC2、数据处理）
  • 强制工具链（必须用哪个 linter、formatter）
  • 行为指令（"Never push directly to main"、"Always run make lint before commit"）

应排除：

  • 个人偏好
  • 项目专属的架构
  • 任何会随项目变化的内容

典型反模式：把整个公司 wiki 复制进去——L1 应该短小（< 100 行最佳），加载时机是每次启动。

示例（来自 managed-settings.json 文档）：

{
  "claudeMd": "Always run `make lint` before committing.\nNever push directly to main."
}

代码示例的中文翻译：

{
  "claudeMd": "提交前始终运行 `make lint`。绝不要直接推送到 main。"
}

3.3 L2 · 用户级（User Memory / Personal Rules）

位置：

系统路径
Claude Code~/.claude/CLAUDE.md（个人）+ ~/.claude/rules/（个人规则）
CursorCursor Settings → User Rules
Cline~/Documents/Cline/Rules/
Roo Code~/.roo/rules/
Aider~/.aider.conf.yml 或 --user-config

作用：用户的个人偏好、跨项目生效的指令。

应包含：

  • user 类型的记忆（个人角色、技术栈偏好）
  • 跨项目生效的工作流（"每次 commit 前跑测试"、"用 TypeScript strict mode"）
  • 沟通风格（"回复用中文"、"不要加 emoji"）
  • 编辑器/工具配置（"用 bun 不用 npm"）

应排除：

  • 任何项目专属内容
  • 任何团队其他人需要遵守的规范
  • 任何可以从 README 推导的内容

典型反模式：在 ~/.claude/CLAUDE.md 写"我们项目用 PostgreSQL"——这是 L3 的内容。

关键引用：

"User-level rules are loaded before project rules, giving project rules higher priority." — Cursor Rules 文档（同样适用于 Claude Code 的 ~/.claude/rules/） 译文： 用户级规则在项目级规则之前加载，因此项目级规则拥有更高优先级。
"Personal rules in ~/.claude/rules/ apply to every project on your machine. Use them for preferences that aren't project-specific." — Claude Code Memory 文档 译文： 放在 ~/.claude/rules/ 的个人规则对本机的每个项目都生效。用于那些不属于特定项目的个人偏好。

实际项目实例（html-report-layout.md，本项目 ~/.claude/projects/-Users-admin-WorkSpace-claude-code/memory/ 下）：

---
name: html-report-layout
description: 长篇 HTML 报告的布局偏好 — 左侧固定 TOC + 右侧主内容滚动
metadata:
  type: feedback
---
**Why:** 用户明确反馈这个布局"挺符合人类操作的"。
**How to apply:**
- 任何长篇 HTML 报告（章节 ≥ 5 节、行数 ≥ 500 行）自动采用此布局
- 短报告不需要侧边栏

这是一个feedback 类型的记忆，scope 应当是 private（个人沟通偏好），与项目无关。

位置：

系统路径加载策略
Claude Code./CLAUDE.md 或 ./.claude/CLAUDE.md启动时全量加载
Claude Code./CLAUDE.local.md同上，但加 .gitignore（个人项目内偏好）
Cursor./.cursorrules 或 ./AGENTS.md 或 ./.cursor/rules/*.mdc启动时全量加载

AGENTS.md 标准./AGENTS.md（仓库根）启动时加载，monorepo 支持嵌套

作用：团队共享的项目规约。commit 进 git，所有人共用。

应包含（与 WHEN_TO_ACCESS 和 Claude Code 内部 TYPES_SECTION_INDIVIDUAL 中 "project" 类型一致）：

  • 项目 (project) 记忆：架构、依赖、构建命令、测试命令、部署流程
  • feedback（team scope）：项目级公约（"测试不能 mock 数据库"）
  • reference：外部系统指针（"bug 在 Linear INGEST 项目"）
  • 项目元信息：负责人、目标用户、关键技术决策

应排除：

  • 用户个人偏好（用 L2）
  • 可从 package.json / README.md / git log 推导的内容
  • 任何"私密"内容（API key、个人 token）

关键引用：

"Treat CLAUDE.md as the place you write down what you'd otherwise re-explain. Add to it when: - Claude makes the same mistake a second time - A code review catches something Claude should have known about this codebase - You type the same correction or clarification into chat that you typed last session - A new teammate would need the same context to be productive" — Claude Code 文档 译文： 把 CLAUDE.md 视作一块黑板——专门写下那些你不想反复解释的内容。出现以下情况时往里加： - Claude 第二次犯同样的错误 - 代码评审抓出了 Claude 早该了解的本代码库知识 - 你在聊天里打出了跟上一次会话相同的一条纠正或说明 - 新同事也需要同样的上下文才能上手

反模式：

  • ❌ 把所有规则都用 globs 切到具体子目录 → 写新文件时拿不到任何指导

5. 关键设计原则（设计良好记忆系统的 7 条规律）

5.1 显式优于隐式

每个记忆文件都应有 frontmatter 声明 scope 和 type。"为什么这是 feedback 而不是 project"如果不写出来，agent 检索时会困惑。

反例：把"团队用 pnpm"写在没有 frontmatter 的 CLAUDE.md 中——既不知道是 private 还是 team，也不知道 type。 正例：

---
name: package-manager-preference
description: Project uses pnpm, not npm. This applies team-wide.
type: project
---

5.2 内容最短、scope 最窄

Boris Cherny（Claude Code 创建者）建议：~100 行是合适的，< 300 行是好上限，> 500 行基本失控（FerroxLabs/agents-md 引用）。

为什么？

  • 越长 agent 越不遵守（"context dilution"）
  • 越长越难 audit
  • 越容易出现矛盾规则

解药：

  • L3 项目级保持 < 200 行
  • L4 路径作用域按需展开
  • L5 MEMORY.md 索引 < 200 行 / 25KB（Claude Code 硬 cap）
  • L2 用户级 < 50 行（个人偏好本就少）

5.3 防止 Drift（记忆腐化）

Drift 是 L5 自动记忆的最大杀手。某条记忆 6 个月前写的，记录"我们用 enzyme 做测试"，但 3 个月前团队全迁到 RTL，这条记忆就成了 trap。

三种防 drift（防记忆腐化）机制：

  • Caveat prompt（Claude Code 模式）：在 system prompt 中加 MEMORY_DRIFT_CAVEAT，要求"使用前验证"。
  • Freshness 警告（memoryAge.ts:33-42）：当记忆 > 1 天时附加 ">N days old" 标签。
  • 结构化声明（memoryAge.ts）：每条记忆带 mtimeMs，被检索时一并返回。
  • 周期性 prune：每条记忆"如果删掉它，agent 会犯什么错？"——如果不会，删掉。

实战经验：html-report-layout.md 是 2026-06-06 写的，仍然新鲜。如果用户切换了布局偏好，agent 应主动更新它——而不是写第二条"新的"。

5.4 Scope 必须显式

混淆 scope 是新用户最常犯的错误。把"我（开发者）用 vim"写进团队 CLAUDE.md，结果其他用 vscode 的同事被强行灌输。

L1/L2/L3 的 scope 边界：

  • L1 managed：所有人、无 exclude
  • L2 user：仅本机、跨项目
  • L3 project：本项目、本地仓库

判断流程：

"这个规则同事需要遵守吗？" - 是 → L3（如果本项目）或 L1（如果是公司强制） - 否 → L2（如果是个人偏好）或 L5（如果是 agent 学到的）

5.5 排除优于包含

WHAT_NOT_TO_SAVE_SECTION（本项目 memoryTypes.ts:183-195）的存在说明：最大的浪费来自"什么都往里塞"。

5 类必须排除：

  • 代码模式 / 架构 / 路径（可由 ls / cat 推导）
  • Git 历史（git log 是权威）
  • 调试 fix（代码本身就是 fix）
  • CLAUDE.md 已有的内容（重复维护导致不一致）
  • 临时任务细节

即使用户明确要求"保存这份 PR 列表"，也要问"有什么 surprising 的？"——只保存那个洞察。

5.6 让 agent 自己维护 L5，但人负责 L3

6. 典型反模式（DO NOT DO）

6.1 把整个 README 复制进 CLAUDE.md

症状：CLAUDE.md 800 行，包含完整 API 文档、贡献指南、tutorial。 问题：README 该是给人看的，agent 跑命令就能看 docs。 解药：CLAUDE.md 只放"agent 必知但 README 不写"的内容（约定、决策、关键反模式）。

6.2 把临时的 debug 笔记写进 MEMORY.md

症状：今天 debug 了一个 race condition，写进 MEMORY.md "to remember"。 问题：这种笔记 99% 是一次性的，3 个月后看会毫无意义。 解药：debug 笔记写在 commit message 或 PR description。如果真的有"非显而易见"的洞察（"我们用 v8 引擎的 microtask 队列有 edge case"），写进 commit message 而非 MEMORY.md。

6.3 写大段"How to use X tool"教学

症状：在 CLAUDE.md 写"Git rebase（变基）用法：..." 问题：agent 训练数据里有大量 rebase 教学；这种内容会稀释关键规则。 解药：信任 LLM 自身能力。CLAUDE.md 只放"我们项目的 git workflow"（"用 squash merge（压缩合并），commit message（提交说明）用中文"）。

6.4 范围错位

症状：

  • 在 ~/.claude/CLAUDE.md（L2）写"我们项目用 PostgreSQL"——这是 L3
  • 在项目 CLAUDE.md（L3）写"我喜欢用 vim"——这是 L2
  • 在 L1 managed 写"个人 token 在 1Password"——这是 L2

问题：scope 错位会导致所有人都被无关规则打扰。 解药：每次写之前问"这个规则有谁需要遵守？"。

6.5 写"我今天做了什么"

症状：MEMORY.md 变成 activity log。 问题：每天自动 append 段落"今天我修了 X bug，refactor 了 Y"。 解药：WHAT_NOT_TO_SAVE_SECTION 显式禁止："Ephemeral task details: in-progress work, temporary state, current conversation context."（译文：临时性任务细节：进行中的工作、临时状态、当前会话上下文。）

6.6 把信任边界当文件类型

症状：在团队 CLAUDE.md 写 API key、密码、内部 URL。 问题：CLAUDE.md commit 进 git，等于把所有 secrets 公开。 解药：

  • secrets → 环境变量 / secrets manager
  • 内部 URL → 用 host 名（如 grafana.internal）而非完整 token
  • 如果必须引用内部资源，明确标注 "do not echo"

6.7 写了规则但从不 prune

症状：CLAUDE.md 一直加，3 年后 800 行。 问题：agent 注意力被稀释，规则遵守率断崖式下降。 解药：每月一次"如果删掉这条，agent 会犯什么错？"——不会的话删掉。

6.8 path-scope 写得过细

症状：每个文件一条 rule，导致 1000 条 rule。 问题：每次启动 context 爆炸；agent 选择困难。 解药：path-scope 按子系统切（src/api/**），不要按文件切（src/api/users.ts）。

  • AGENTS.md 普及度研究：gh search 统计近 12 个月新增仓库采用 AGENTS.md 的比例。

11. 总结

AI Coding Agent 的记忆系统在过去 18 个月从"完全无"快速演化到"6 层 + 4 类 + drift 防护"的成熟形态。本报告把 8 个代表系统的实践抽象为：

  • 6 层模型（Hook 钩子 / Managed 托管 / User 用户 / Project 项目 / Path-scoped 路径作用域 / Auto 自动 / Session 会话内）
  • 4 类记忆（user 用户 / feedback 反馈 / project 项目 / reference 参考）
  • 3 类失败模式（drift 记忆腐化 / 膨胀 / scope 错位）
  • 1 套正交工具（symlink + @ 导入实现 AGENTS.md ↔ CLAUDE.md 互通）

最关键的 3 条结论：

  • 能由 git log / 当前代码 / 文档推导出来的内容不要写进记忆——这是反模式的根因。
  • 每个记忆应有 frontmatter 显式声明 scope 和 type——否则 agent 检索时会困惑。
  • MEMORY.md 是索引，不是记忆——具体内容在分散的主题文件里，索引必须 < 200 行 / 25KB。

最值得自建系统照搬的：

  • Claude Code 的 4 类记忆 + 双重容量限制 + 防腐化机制 + 智能检索
  • AGENTS.md 作为跨框架的"主文件 + 工具特定补丁"模式
  • "Why / How to apply" 双行结构（feedback / project 类记忆的标配）

最不该照搬的：

  • Cursor 的 4 种 apply mode（复杂度太高，新用户驾驭不了）
  • Aider 的 --read 显式列表（缺乏发现性，每次要手动加）
  • GitHub Copilot 的 applyTo: 单字段（不如 paths: 数组灵活）

最该避免的：

  • 把 README 复制进 CLAUDE.md
  • 把临时 debug 笔记写进 MEMORY.md
  • 写"我今天做了什么" activity log
  • 从不 prune
