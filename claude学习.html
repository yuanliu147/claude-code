引言:为什么是 Harness

Claude Code 本质上是一个 "围绕一个常量循环 + 动态可扩展的 Harness"。 核心循环 50 行就能写完,所有复杂度都来自"循环外面"——工具、上下文、权限、UI、状态、Provider 抽象。

Agent 智能体的质量,90% 取决于 Harness 工程,而不是模型本身。 本报告不讲目录结构,只讲具体哪一行在做什么、为什么这样做、生产上哪里踩过坑。

一、Agent Loop 的真正状态机

表面上看 queryLoop 就是一个 while (true), 但内部是带类型化 transition 标签的状态机。

State 对象的 9 个字段

位置:src/query.ts:204-218

// 在循环迭代之间携带的可变状态
type State = {
  messages: Message[]
  toolUseContext: ToolUseContext
  autoCompactTracking: AutoCompactTrackingState | undefined
  maxOutputTokensRecoveryCount: number          // 0-3 熔断
  hasAttemptedReactiveCompact: boolean            // 防止反复尝试
  maxOutputTokensOverride: number | undefined
  pendingToolUseSummary: Promise<ToolUseSummaryMessage | null> | undefined
  stopHookActive: boolean | undefined
  turnCount: number
  // Why the previous iteration continued. Undefined on first iteration.
  // Lets tests assert recovery paths fired without inspecting message contents.
  transition: Continue | undefined

7 个 continue 站点与 Continue 标签

每次迭代结束不是"赋值 9 个字段",而是 state = { ...state, ..., transition: { reason: '...' } }。 在 query.ts 里我数到至少 7 个 continue 站点,每个站点都打不同的 reason 标签:

transition 字段的可测性含义(深入)

这是反直觉的设计取舍。常规做法是:恢复路径完成时,往 messages 数组里追加一条特殊消息,或者打 log。 缺点:

  • 消息追加需要从消息内容推断"发生了什么",脆弱(消息文本改了测试就挂)。
  • 日志是 fire-and-forget,测试无法同步断言。
  • 返回值是 terminal,但恢复是 continue,不返回。

Claude Code 的做法是:把"为什么 continue"作为一个结构化字段持久化在 State.transition 里。 字段是判别联合(discriminated union),带 reason + 元数据: 

// 实际从 query.ts 抄出来的两个 continue 站点
// 站点 A: max_output_tokens escalation
transition: { reason: 'max_output_tokens_escalate' }

// 站点 B: max_output_tokens 多轮恢复(带 attempt 计数)
transition: {
  reason: 'max_output_tokens_recovery',
  attempt: maxOutputTokensRecoveryCount + 1,  // 第几次尝试
}

// 站点 C: context collapse drain(带 drained count)
transition: {
  reason: 'collapse_drain_retry',
  committed: drained.committed,  // drain 出去多少条
}

这样测试就能写: 

// 伪测试
const result = await runQueryToCompletion({ input: hugeOutput })
expect(result.lastTransition).toEqual({
  reason: 'max_output_tokens_recovery',
  attempt: 2,   // 第二次重试
})

这是用"代码噪音"换"测试确定性"。每个 continue 站点多写一行 transition: {...}, 但回报是:7 条恢复路径每一条都能独立测试,不需要"读 messages 数组第 N 条判断事件是否发生"。

关键洞察

"为可测性牺牲可读性"是工程上的反向直觉——通常认为可读性比可测性更重要。 但 Claude Code 的取舍是:recovery 路径必须被独立测试,因为它们的失败成本极高 (例如 3 次 compact 失败会浪费 250K/日 API 调用,见第三节)。 transition 字段就是为这种高失败成本、低发生频率的路径设计的最小可观测性。

具体例子:max_output_tokens_recovery 恢复路径

两个时间点的语义

"恢复路径开始" = 第 ① 步,if 判断通过,进入恢复分支;
"恢复路径完成" = 第 ⑦ 步,continue 之前,transition 已经被写好。

整个恢复路径是一个不可分割的事务: 要么 ⑦ 步成功,带着新 transition 进入下一轮; 要么中途抛错,这一轮没写 transition(测试可以从"transition 还是上一次的"推断出"恢复路径未完成")。

✅ Claude Code 的做法:打 transition 标签

代码里多了一行:transition: { reason, attempt }

测试可以这样写(干净):

test('recovers from max_output_tokens on 2nd attempt', async () => {
  // 构造会触发 2 次恢复的场景
  const loop = runQueryToCompletion({ input: '总结 100 页文档' })

  // 消费完所有事件,跑到 loop 退出
  for await (const event of loop) { /* ... */ }
  const finalState = await loop.return()

  // ✅ 直接断言:最后一次 continue 的标签
  expect(finalState.transition).toEqual({
    reason: 'max_output_tokens_recovery',
    attempt: 2,  // ⬅️ 精确知道是第 2 次重试
  })
})

test('stops after 3 recovery attempts (circuit breaker)', async () => {
  const loop = runQueryToCompletion({ input: '永远写不完的总结' })
  for await (const event of loop) { /* ... */ }
  const finalState = await loop.return()

  // ✅ 熔断器生效?直接断言
  expect(finalState.maxOutputTokensRecoveryCount).toBe(3)
  // 且最后一次 transition 不应该是 recovery
  expect(finalState.transition?.reason).not.toBe('max_output_tokens_recovery')
})

test('reactive compact retry path fires on 413', async () => {
  const loop = runQueryToCompletion({ mockError: '413_prompt_too_long' })
  for await (const event of loop) { /* ... */ }
  const finalState = await loop.return()

  // ✅ 跟 max_output_tokens 完全不同的 recovery 路径
  // 不需要看 messages 内容,直接看 transition
  expect(finalState.transition?.reason).toBe('reactive_compact_retry')
})

为什么好:

  • 断言目标是结构化对象,不是字符串
  • 不同 recovery 路径互不干扰——测 max_output_tokens 不会误判 compact retry
  • 测试是集成测试(跑整个 loop),但断言是精确的(看 transition),不损失覆盖度
  • 新加一个 recovery 路径(比如 stop_hook_blocking),只需要 expect(transition.reason).toBe('stop_hook_blocking')

为什么"非显然"

第一直觉:恢复路径完成后,我已经把恢复消息放进 messages 了,测试可以从那里读啊,何必多此一举打 transition?

答案:恢复消息只是给模型看的指令("Resume directly"),不是给测试看的信号。 把"给模型看的"和"给测试看的"混在同一个数组里:

  1. 耦合——你改 prompt 措辞,测试就挂(这叫"测试和实现细节绑死")
  2. 歧义——同一条消息可能由不同路径生成
  3. 不可穷举——你想测"是否走了 compact retry",得知道 compact 路径用什么消息; 但 compact 路径会根据上下文动态生成消息

transition 字段是专门为测试设计的旁路信号:

  • 它跟 messages 完全解耦
  • 它的 reason 跟恢复路径 1:1 绑定
  • 它的元数据(attempt、committed)是测试断言需要的精确数据

代价:每个 continue 多写一行。回报:7 条恢复路径每一条都能干净地独立测试。

更深的类比:这个设计你大概率已经见过了

  • React Redux 的 action.type:{ type: 'MAX_TOKENS_RECOVERY', payload: { attempt: 2 } }——同样的判别联合
  • HTTP 响应的 status 字段:你从 200/404/500 知道发生了什么,不用 parse body
  • 数据库事务的 isolation level:SERIALIZABLE vs READ_COMMITTED——同样是给上层断言用的元数据

这些都是"为可观测性而存在的元数据字段",跟业务数据正交。 transition 在 Claude Code 的 loop 里扮演完全相同的角色。

二、StreamingToolExecutor —— 流式 + 并行的真正难点

位置:src/services/tools/StreamingToolExecutor.ts

四态机 + 并发隔离

type ToolStatus = 'queued' | 'executing' | 'completed' | 'yielded'

type TrackedTool = {
  id: string
  block: ToolUseBlock
  assistantMessage: AssistantMessage
  status: ToolStatus
  isConcurrencySafe: boolean
  promise?: Promise<void>            // 并行执行的去重句柄
  results?: Message[]
  pendingProgress: Message[]
  contextModifiers?: Array<(ctx: ToolUseContext) => ToolUseContext>
}

关键的并发控制逻辑(行 129-150):

private canExecuteTool(isConcurrencySafe: boolean): boolean {
  const executingTools = this.tools.filter(t => t.status === 'executing')
  return (
    executingTools.length === 0 ||
    (isConcurrencySafe && executingTools.every(t => t.isConcurrencySafe))
  )
}

private async processQueue(): Promise<void> {
  for (const tool of this.tools) {
    if (tool.status !== 'queued') continue
    if (this.canExecuteTool(tool.isConcurrencySafe)) {
      await this.executeTool(tool)
    } else {
      if (!tool.isConcurrencySafe) break  // ⬅️ 顺序敏感工具必须按序
    }
  }
}

这意味着 LLM 一次返回的 5 个工具被分成两批:

  • 第 1 批:isConcurrencySafe === true 的工具(读文件、grep、glob...)→ 并行启动
  • 第 2 批:isConcurrencySafe === false 的工具(写文件、bash)→ 独占执行且保留原始顺序

isConcurrencySafe 是工具 + 输入的纯函数

// StreamingToolExecutor.ts:104-113
const parsedInput = toolDefinition.inputSchema.safeParse(block.input)
const isConcurrencySafe = parsedInput?.success
  ? (function() {
      try {
        return Boolean(toolDefinition.isConcurrencySafe(parsedInput.data))
      } catch {
        return false            // 判定函数抛错 = 视为不安全
      }
    })()
  : false                            // 解析失败 = 不安全

这就是为什么 Bash 工具能根据命令(读 vs 写)决定自己能否并行。 写命令返回 false,独占执行。框架不替工具猜并发语义。

Sibling abort 失败传染

// StreamingToolExecutor.ts:45-48

Bash 工具出错时,正在并行执行的兄弟 Bash 立刻被 kill,但不影响 query 整体的继续运行。 父子两层 AbortController 是异常传播策略与用户取消策略的清晰分离。

面试话术

"Claude Code 用一个自定义的 StreamingToolExecutor 同时解决了三个问题:流式展示(文本一返回就 yield)、 并行执行(独立工具并发)、失败传染(兄弟进程连带 abort)。 isConcurrencySafe 是个纯函数,从工具定义 + 输入就能判定—— 这个设计让工具作者自己决定并发语义,框架不替它猜。"

给压缩自身保留 20K 输出空间,因为 p99.99 的压缩总结要 17,387 tokens。 这个数字是跑出来的,不是拍脑袋。

死循环防御(递归死锁)

四种 querySource 显式排除,防止"压缩任务在压缩任务里嵌套 compact"的死锁。

三层压缩的协调顺序

// query.ts:401-447
// 1. snip(尾部裁剪,feature-gated)
if (feature('HISTORY_SNIP')) { ... }

三套规则不是 if-else,是各自独立的 rule source map(从 settings.json / .claude/permissions/ / session 内 /permissions 命令 三处加载)。

  ? Promise.resolve(forceDecision)
  : hasPermissionsToUseTool(tool, input, toolUseContext, assistantMessage, toolUseID)

decisionPromise.then(async (result) => {
  if (result.behavior === "allow") { /* 立即执行 */ }
  if (result.behavior === "deny")  { /* 注入 tool_result 错误,继续 loop */ }
  if (result.behavior === "ask")   { /* 路由到 3 个 handler 之一 */ }
})

"Claude Code 的权限不是单一 if 判断,而是一个分层路由系统: 5 种模式 × 4 类规则 × 3 个 handler。 规则按 source 维度(map)加载,行为按调用者身份路由(交互/协调者/worker), ask 路径下还有 speculative classifier 把 LLM 判定隐藏在 UI 弹窗的渲染时间窗里。 用户感知的延迟不等于系统的判定时间。"

五、Tool 接口:Zod 三用 + 描述函数化

位置:src/Tool.ts:358-399

export type Tool<Input, Output, P> = {
  aliases?: string[]                         // 工具重命名的向后兼容
  searchHint?: string                        // ToolSearch 关键词,3-10 词
  call(args, context, canUseTool, parentMessage, onProgress): Promise<ToolResult>
  description(input, options): Promise<string>  // ⬅️ 函数,不是常量
  readonly inputSchema: Input             // Zod
  readonly inputJSONSchema?: ToolInputJSONSchema  // MCP 工具专用
  outputSchema?: z.ZodType<unknown>
  inputsEquivalent?(a, b): boolean
  isConcurrencySafe(input): boolean
  isEnabled(): boolean
  isReadOnly(): boolean
  isMcp?: boolean
  maxResultSizeChars?: number
  userFacingName(input): string
  renderToolResultMessage?(...)
  renderToolUseMessage?(...)
}

真正值得说的两个细节

1. description 是函数不是常量

description(input: z.infer<Input>, options: {
  isNonInteractiveSession: boolean
  toolPermissionContext: ToolPermissionContext
  tools: Tools
}): Promise<string>

同一个工具,在 CI 模式 vs 交互模式,描述会不一样。 比如 BashTool 在 non-interactive session 下不会让用户看到"是否保存到允许列表"的提示语,描述会动态省略相关引导。

2. inputSchema 三用

readonly inputSchema: Input   // Input extends z.ZodType<{...}>
  • 类型推导:z.infer<Input> 给 call() 的 args
  • 运行时校验:toolDefinition.inputSchema.safeParse(block.input)
  • API 序列化:toolDefinition.inputSchema 转换成 JSON Schema 发给 LLM

一个 Zod schema 同时是 TypeScript 类型 + 校验器 + LLM 工具描述的真相来源。

3. canUseTool 作为工具 call 的第三参数传进去

call(
  args: z.infer<Input>,
  context: ToolUseContext,
  canUseTool: CanUseToolFn,          // ⬅️ 工具内部可触发子权限检查
  parentMessage: AssistantMessage,
  onProgress?: ToolCallProgress<P>,
): Promise<ToolResult<Output>>

工具在执行过程中,可能自己需要调用其它工具(比如 AgentTool 在跑子任务时会用 Task)。 把 canUseTool 透传进去,让子调用走和顶层一样的权限链路。

洞察

"Claude Code 的 Tool 接口把'描述做成函数'这一点很容易被忽视—— description(input, options) 是异步的,可以根据 input 动态生成。 在 CI vs REPL 模式下,同一个工具给 LLM 看的描述是不一样的。 Tool schema 的真相来源必须是同一个 Zod 对象,否则 LLM 看到的和实际校验的会漂移。"

Stop hook 的"超 8 次覆盖"机制

来自 Anthropic 官方 best-practices:

A Stop hook runs your check as a script and blocks the turn from ending until it passes. Claude Code overrides the hook and ends the turn after 8 consecutive blocks.

这是护栏的护栏:用户写一个 Stop hook 强制 Claude 跑测试再停, Claude 跑了 8 次测试还不通过,系统强制让 Claude 停下,避免死循环。

洞察

"Hooks 跟 CLAUDE.md 提示词的核心区别是确定性: 提示词是软的(模型可能忽略),Hook 是硬的(代码执行)。 但 Hook 自己又需要一个熔断(8 次连续阻止后强制放行)—— 所有的硬约束都需要软熔断,否则用户可以把 Agent 锁死。"

八、子 Agent Fork 共享 prompt cache

位置:src/tools/AgentTool/forkSubagent.ts

Fork 缓存共享的关键代码

// Tool.ts:297
renderedSystemPrompt?: SystemPrompt

注释极重要:

Parent's rendered system prompt bytes, frozen at turn start. For fork subagents to share parent's prompt cache — re-invoking getSystemPrompt() at fork-spawn could diverge (GrowthBook cold→warm) and break the cache.

工程含义

  1. 系统 prompt 在 turn 开始时冻结到 toolUseContext.renderedSystemPrompt
  2. Fork 时直接复用父级的字节流
  3. 让"父 Agent + 10 个并行子 Agent"能共享同一份 prompt cache,不是 10 份
洞察

"子 Agent 的 fork 机制里最隐蔽的设计是'冻结父级 systemPrompt'。 不是 fork 时再渲染一次,那样会因为 GrowthBook cold→warm 击穿 prompt cache。 缓存命中的前提是字节级一致,所以子 Agent 必须继承父级的字节流。 这是 prompt caching 在多 Agent 场景下能否起效的关键。"

九、AbortController 两层树

位置:src/utils/abortController.ts、StreamingToolExecutor.ts:59-61

// 用户按 ESC → 顶层的 toolUseContext.abortController
// 某个 Bash 失败 → StreamingToolExecutor 的 siblingAbortController

this.siblingAbortController = createChildAbortController(
  toolUseContext.abortController,
)

createChildAbortController(parent) 实现的是 single-child abort tree:

  • 父被 abort → 子立刻 abort(整体取消)
  • 子被 abort → 父不会自动 abort(局部失败,不终止整个 turn)

这是异常传播策略与用户取消策略的清晰分离。

附录 B:面试 5 个追问的回答骨架

Claude Code 的 Agent Loop 长什么样?
循环本身 50 行。复杂度全在 loop 外面:流式工具执行的并发控制用 StreamingToolExecutor,上下文三层压缩 + 熔断,5 模式权限路由,Hook 扩展点不侵入 loop。
流式返回怎么处理并行工具?
StreamingToolExecutor 把工具分成 queued/executing/completed/yielded 四态。isConcurrencySafe 是工具 + 输入的纯函数,框架不替工具猜。兄弟 abort 用 child-of-parent 树结构,失败传染不污染主循环。
上下文怎么管理?
三层:snip(尾部裁剪)→ microcompact(按 tool_use_id 计 token,不动内容)→ autocompact(LLM 总结,留 20K 给总结自身输出)。三个机制正交,不会互相干扰。生产数据显示连续 compact 失败会浪费 API,所以 3 次熔断。
工具怎么定义?
Zod schema 一份,三用:类型推导、运行时校验、给 LLM 看。description 是函数不是常量,可以根据 input 和 session 模式动态生成。canUseTool 透传到工具内部,让子调用走同一套权限链。
多 LLM 怎么兼容?
在 Adapter 出口定义内部事件流协议(BetaRawMessageStreamEvent),三个 Provider 都归一化到这层。下游零修改。新增 Provider 只写入向转换。
