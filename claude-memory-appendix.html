这份附录是为谁写的？
如果你读完两份主报告后还有"等等，那这个到底是怎么工作的？"的疑问，这篇就是答案。8 个章节每章独立，可以跳着读。每章结尾有一个"实操建议"小节——告诉你"作为用户该怎么用"。

1. AI 怎么自己写记忆？

主报告说"agent 学到东西就自动写"，但没说具体什么时候、怎么写、谁批准。这是记忆系统的"主动脉"——不讲透就不知道什么时候该信任 MEMORY.md 里的内容。

1.1 触发时机：每个对话轮次结束（不是 session 结束）

很多人以为"会话结束才整理记忆"——其实不是。每次你发完一条消息、agent 回复完（最后一轮没有工具调用），就会触发一次自动提取。具体由 stopHooks.ts:141-153 监听，调用 extractMemories 模块。

这个调用是 fire-and-forget（异步不阻塞）——你看不到等待，agent 已经把回复渲染给你看了，记忆提取在后台跑。

它只为主代理跑，不为子代理跑。 extractMemories.ts:531-534 检查 toolUseContext.agentId，如果有值（说明是子代理在跑）就跳过。这是为了避免"子代理的小决策污染主代理的长期记忆"。

1.2 写哪些内容：四种类型 + 五类排除

提取出来的内容会被归类成四种之一（每种都有明确的"什么时候写"指南）：

类型什么时候写典型例子
user用户透露角色 / 知识背景 / 偏好"我是前端工程师，主要用 React"
feedback用户纠正或确认 agent 的做法"不要每次都加日志" / "对，就这样"
project项目动态、谁在做什么、为什么"Q1 移动端发版，所以合主要冻结"
reference外部系统指针"bug 在 Linear INGEST 项目里"

同时有五类明确禁止保存的内容：

  • 代码模式、架构、文件路径（可从当前代码状态推导）
  • Git 历史（git log 才是权威）
  • 调试 fix 方案（fix 在代码里，commit message 有上下文）
  • CLAUDE.md 里已有的内容（重复维护会导致不一致）
  • 临时任务细节、当前对话上下文（用 Plan / Tasks 即可）

1.3 写到哪里：分散的 .md 文件 + 索引

记忆不是"塞进 MEMORY.md"——而是：

1 每个记忆写成独立 .md 文件，如 user_role.md、feedback_testing.md，带 frontmatter（name、description、type）
2 在 MEMORY.md（入口索引）里加一行指针：- [Title](file.md) — one-line hook

这样做的好处：每次启动只加载 MEMORY.md（小、200 行 / 25KB 上限），具体记忆按需展开。

1.4 软上限和"互斥"机制

虽然没有"单次写多少"的硬限制，但有几个软约束：

  • 提取用的子代理最多 5 轮（extractMemories.ts:426），防止它在记忆系统里转圈
  • 扫描现有记忆时最多看最新的 200 个（memoryScan.ts:21）
  • 有节流阀：默认每 1 个 eligible 轮次跑一次，可配（extractMemories.ts:374-385）

还有一个很聪明的设计：主代理和后台提取互斥。如果主代理在本轮自己写了记忆（通过 system prompt 里的 save 指令），后台提取会跳过（extractMemories.ts:345-360）。这样你可以说"记住这个"——主代理立刻写，后台不会重复写。

1.5 写错了怎么办？

没有自动 undo / rollback 机制。 记忆文件就是普通 .md 文件，写错只能手动编辑或删除。

但有以下审计/可见性：

  • extractMemories.ts:473 等几个 telemetry 事件记录"提取了多少条、用了多少 token、耗时多少"——但只发到 analytics，不存 Git，无法通过 git revert 撤回
  • 用户可以用 /memory 命令浏览所有记忆文件，手动改
实操建议：每 1-2 个月打开 ~/.claude/projects/<你的项目>/memory/ 看一眼 MEMORY.md 和主题文件。删掉过时的、合并重复的。这是"记忆系统卫生"。

2. AI 怎么从一堆记忆里挑出对当下有用的？

主报告说"AI 召回相关记忆"，但没说召回的精妙设计。这背后有个很有意思的"小 AI 选 → 大 AI 用"两阶段架构——不讲透会以为"记忆系统 = 简单检索"。

2.1 三步流程（白话版）

1 扫描：scanMemoryFiles() 读 memory 目录下所有 .md，按修改时间倒排，最多 200 个，提取每个文件的 frontmatter（前 30 行）作为清单
2 格式化：把清单格式化成一段文本，类似：
- [user] user_role.md (2026-06-01): 前端工程师，...
- [project] deploy.md (2026-06-02): 部署流程，...
3 选 top-5：用另一个小模型（Sonnet 级别）看这个清单 + 你的问题，挑出最相关的 5 个文件名。强制 JSON schema 输出 { selected_memories: string[] }

为什么不让大模型（你正在对话的那个）直接看所有记忆？因为记忆可能很多，全塞进 context 太贵。用小模型先"过滤"是个聪明的工程权衡——用便宜的小模型做筛选，让贵的大模型只读相关的。

2.2 选了但不相关、漏了但相关，怎么办？

这是召回机制的固有缺陷。选错的代价：

  • 选了 5 个但其实你问的是第 6 个 → 大模型看到的是不相关的记忆 → 回复质量下降
  • 漏选 → 大模型"不知道"有这条记忆 → 你以为它没记住
实际上"漏选"是常态。 小模型用清单（文件名 + 一句话描述）做选择，描述越准越好。MEMORY.md 里那条"one-line hook"写得越具体，越容易被选上——所以 好的 MEMORY.md 不是简单的"指向"，而是"精准描述"。

2.3 还有一个防重机制

同一轮对话中，已经被选过的记忆文件不会再次被选——alreadySurfaced 集合过滤（findRelevantMemories.ts:46-48）。这避免 agent 在同一次回复里反复引用同一记忆。

2.4 失败时怎么办？

selector 失败（Sonnet 报错、超时、JSON 解析失败）会静默返回空数组——不阻塞主流程（findRelevantMemories.ts:131-140）。主代理的回复还是会给出来，只是没有"记忆辅助"。

实操建议：如果你发现"我明明让 agent 记住 X 了，它怎么又问我同样的问题？"——大概率是 X 的描述太宽泛，没被 Sonnet selector 选中。把 X 的"description"字段写得更具体（如"用户在 2026-06-06 决定：每周五下午固定做 code review"），selector 选中率会高很多。

3. 子代理（Task）有自己的记忆吗？

主报告提到"subagents can also maintain their own auto memory"——但没说怎么用、什么时候有、什么时候没有。这是很多用户踩坑的地方：明明用了 Task 工具让子代理做调研，子代理写进自己记忆的东西主代理"看不到"。

3.1 简短答案：大部分子代理没有，只有显式启用的才有

built-in 子代理（general-purpose、Explore、Plan 等）默认都没有独立记忆。 它们不挂载任何持久记忆——每次启动从零开始。

如果你用自定义 agent（自己写的 .md 文件或 JSON 配置），在 frontmatter 里加一行：

---
name: my-researcher
description: 调研类任务的代理
memory: user  # 或 project / local
---

这样这个 agent 才会有自己的记忆。解析发生在 loadAgentsDir.ts:593-605，然后 getSystemPrompt() 会把它的 MEMORY.md 内容拼进 system prompt（loadAgentsDir.ts:726-732）。

3.2 子代理的记忆存哪里？

跟主代理完全分开，有三种 scope：

Scope路径跨项目？进 Git？
user~/.claude/agent-memory/<agentType>/MEMORY.md✅❌
project<cwd>/.claude/agent-memory/<agentType>/MEMORY.md❌✅
local<cwd>/.claude/agent-memory-local/<agentType>/MEMORY.md❌❌（gitignored）

主代理的自动记忆在 ~/.claude/projects/<项目>/memory/，跟子代理完全独立，不共享同一文件。

3.3 主代理能读子代理记忆吗？

理论上能——子代理记忆本质是磁盘上的 MEMORY.md 文件，主代理只要有 Read 工具就能读。但这不是内置行为，没有代码会自动把子代理记忆注入主代理 context。

反过来：子代理不能读主代理记忆。子代理启动时 context 为空（除非是 fork 子代理），它只拿到 prompt 参数里的任务描述。主代理的 memory/ 目录不会自动进入子代理视线。

3.4 多个子代理之间呢？

默认不共享。每个子代理的 agentType 是独立目录名（agentMemory.ts:56）。

唯一共享路径是 team memory：<autoMemPath>/team/。但这是 TEAMMEM feature 开启时的特殊机制，普通子代理用不到。

3.5 子代理的记忆满了怎么办？

限制跟主代理完全一样：200 行 / 25KB（memdir.ts:35-38）。子代理和主代理共用同一套 truncation 逻辑（truncateEntrypointContent）。

3.6 子代理的 extractMemories 跑吗？

不跑。extractMemories.ts:531-534 明确检查 toolUseContext.agentId，如果有值（说明是子代理）就跳过。

这意味着：子代理的"自动记忆"其实是"半自动"——它需要自己通过 FileWriteTool 手动写 MEMORY.md，后台提取不会自动填充。这是产品设计上的取舍：避免子代理的临时决策污染长期记忆。

实操建议：如果你想让某个子代理积累知识，在它的 prompt 里明确告诉它"完成任务后把要点写到 MEMORY.md"。否则它的"记忆"永远是空的。

4. 夜间 /dream 做了什么？

主报告说"夜间整理"，但没说具体什么时间触发、怎么整理、错了怎么办。这是"白天的便签怎么变成团队知识库"的关键转换。

4.1 两套机制并存：手动 + 自动

  • 手动 /dream：你输入 /dream，立即跑（dream.ts:25 标记为 userInvocable: true）
  • 自动 autoDream：后台以子代理形式触发，限制 Bash 只读（autoDream.ts:2-3）

4.2 自动版的三道门（由便宜到贵）

门条件默认值
时间门距上次合并 ≥ 多少小时24 小时
会话门自上次合并以来新会话数 ≥ 多少5 个
锁门没有其他进程正在合并—

三道门都通过才会启动子代理执行（autoDream.ts:141-190）。

4.3 /dream 怎么工作？4 阶段

1 Orient（定位）：先 ls memory 目录，读 MEMORY.md（索引），扫已有的主题文件
2 Gather（收集）：优先读 logs/YYYY/MM/YYYY-MM-DD.md（每天的 append-only 日志），其次扫现有记忆中与代码矛盾的事实，需要具体上下文才去 grep transcripts（jsonl）
3 Consolidate（整合）：合并进已有主题文件（不创建近邻新文件），删除被证伪的记忆，把相对日期转成绝对日期
4 Prune（剪枝）：保持 MEMORY.md ≤ 200 行 / 25KB，每条目 ≤ 150 字符，详情移入主题文件

4.5 怎么决定"哪些合并、哪些删除"？

全权交给 LLM 判断。prompt 里没有精确算法——没有 embedding 相似度、没有 TF-IDF。LLM 自己读、自己判断（consolidationPrompt.ts:49-51）。

这意味着：/dream 的"整理质量"取决于 LLM 本身。同一个内容不同 LLM 整理结果可能差很多。

4.6 出错了怎么办？

有锁机制作为安全网，但没有版本备份。 流程是：
  1. 子代理执行前先获取锁（PID 写入 lock 文件）
  2. 出错时 catch 块回滚锁的 mtime（consolidationLock.ts:91-108）
  3. 时间门再次通过，下次自动重跑

但：子代理已经写过的部分内容不会被回滚。锁回滚只影响"下次触发时间"，不恢复已写的文件。没有 git-based undo。

4.7 能手动撤销吗？

用户可以在 Shift+Down 对话框中止正在跑的 dream 任务（DreamTask.ts:136-156），但这只中止子代理 + 回滚锁 mtime，不撤销已写的文件。

实操建议：
  • 想立刻整理：/dream
  • 不放心自动整理：把 memory/ 目录加进 Git，每次 /dream 之后 git diff 一下
  • 发现 /dream 写错了：手动编辑对应 .md 文件（~/.claude/projects/<项目>/memory/<主题>.md）

5. 安全机制到底在防什么？

主报告提到"path validation"，但没说清楚具体在防什么攻击、怎么防。这是把记忆系统部署到团队时最敏感的问题——不讲透团队不会敢用。

5.1 防三类攻击

A. 路径越界（path traversal）

攻击：让 agent 写入 ../../etc/passwd、~/.ssh/ 等敏感位置

防御：validateMemoryPath（paths.ts:109-150）五重检查：

  • 拒绝相对路径（../foo）
  • 拒绝根目录和接近根的路径（/、/a）
  • 拒绝 Windows 盘符根（C:\）
  • 拒绝 UNC 路径（\\server\share）
  • 拒绝 null byte（\0）
B. 符号链接逃逸（symlink escape）

攻击：在团队记忆目录里建一个符号链接 team/secrets → /etc/，让 agent 通过这个链接写入任意文件

防御：realpathDeepestExisting（teamMemPaths.ts:109-171）从文件向上遍历，对每个祖先目录调 realpath() 解析真实路径，再比较真实路径是否仍在团队目录内。还检测悬空符号链接（ELOOP）。

C. 注入向量（injection）

攻击：通过 autoMemoryDirectory 注入恶意路径

防御（teamMemPaths.ts:22-64 sanitizePathKey）：

  • URL 编码遍历：%2e%2e%2f → ../，解码后检测 .. 或 /
  • Unicode 归一化攻击：全角字符 ． 归一化后变 ..，检测归一化前后差异
  • 反斜杠拒绝（Windows 路径分隔符作为穿越向量）
D. settings.json 路径注入

攻击：在项目 .claude/settings.json（会提交到代码库）里设 autoMemoryDirectory: "~/.ssh"，让所有协作者把记忆写到 ~/.ssh/

防御：projectSettings 被故意排除，只从 trusted sources（policySettings / flagSettings / localSettings / userSettings）读取 autoMemoryDirectory。

5.2 个人 vs 团队记忆的隔离

物理路径：

  • 个人：~/.claude/projects/<项目>/memory/
  • 团队：~/.claude/projects/<项目>/memory/team/

隔离机制是文件系统级：写入时做两遍检查（fast 字符串 + realpath 解析），读取时只检查字符串前缀（读取不涉及符号链接逃逸风险）。

team memory 明确禁止保存敏感数据（teamMemPrompts.ts）。规则里写明：never save API keys or user credentials。
实操建议：
  • 把 API key、个人 token 等敏感信息只写进个人记忆或环境变量，绝不写团队记忆
  • 团队记忆里只放"团队所有人都该知道"的项目规约、外部系统指针、共享的决策
  • 定期 git diff .claude/agent-memory/ 看看队友有没有意外提交了敏感信息

6. 怎么关掉记忆系统？

主报告没专门讲"开 / 关"。不是每个人都想要 agent 自动学习——给用户选择权是基本产品设计。

6.1 三档控制

档位触发方式效果
全关 CLAUDE_CODE_DISABLE_AUTO_MEMORY=1 整个记忆系统关闭：extractMemories、autoDream、/remember、/dream、team sync 全部停用
bare 模式 --bare（设置 CLAUDE_CODE_SIMPLE=1） 同全关，且 CLI 界面极度精简（无 ASCII art、无 TUI 装饰）
只关 auto memory，保留 CLAUDE.md settings.json: { "autoMemoryEnabled": false } 仅关闭 auto memory（MEMORY.md 系统），CLAUDE.md 规则系统不受影响

优先级（paths.ts:30-55）：env var > bare > remote 检测 > settings.json > 默认开启

关闭 auto memory 不等于关闭 CLAUDE.md。两者是独立的系统。CLAUDE.md 由 claudemd.ts 的 getMemoryFiles() 管理，不受 isAutoMemoryEnabled() 控制。

6.2 关闭后会失去什么？

组件关闭时行为
loadMemoryPrompt()返回 null，系统提示词中不注入任何记忆指令
getMemoryFiles()跳过 AutoMem/TeamMem entrypoint 的读取
isExtractModeActive()返回 false，背景提取不跑
/remember 技能不可用
/dream 技能不可用
team memoryisTeamMemoryEnabled() 返回 false

CLAUDE.md 系统完全不受影响——你仍然能写项目级规则、加载路径作用域规则。

实操建议：
  • 新项目先用 1-2 周记忆系统收集经验，再决定保留还是关
  • 对噪音敏感（不想被 auto memory 干扰）→ 选"只关 auto memory，保留 CLAUDE.md"
  • 完全不用 AI 记忆概念（极简主义）→ 选"全关"

7. 记忆满了会怎样？

主报告提到"200 行 / 25KB 双 cap"，但没说截断后被丢的部分会丢吗、用户能主动清理吗。用了 6 个月后 MEMORY.md 会膨胀——你得知道"我得手动管"还是"系统会帮我管"。

7.1 MEMORY.md 是索引，不是存储

系统不把记忆内容直接写进 MEMORY.md。它是这样的：

  • 每个记忆是一个独立的 .md 文件（user_role.md、feedback_testing.md 等）
  • MEMORY.md 只含指针索引：- [Title](file.md) — one-line hook

所以"满"是指索引文件本身满了，不是记忆内容满了。

7.2 满了的硬限制

  • 最多 200 行（MAX_ENTRYPOINT_LINES，memdir.ts:35）
  • 最多 25,000 字节（MAX_ENTRYPOINT_BYTES，memdir.ts:38）

7.3 超限后会发生什么？

1 按行截断：从第 200 行处切断（truncateEntrypointContent，memdir.ts:57-103）
2 再按字节截断：截断后若还超 25KB，在最后一个换行符处切断（避免切断 mid-line）
3 追加警告：
> WARNING: MEMORY.md is X lines (limit: 200). Only part of it was loaded.

7.4 被截掉的部分丢了吗？

没有！ MEMORY.md 只是索引——被截掉的行是指向记忆文件的指针，对应的 .md 主题文件还在 ~/.claude/projects/<项目>/memory/ 目录里。

截断只影响本次对话的上下文加载，不影响磁盘文件本身。所以你下次看到 MEMORY.md 满了，不要去删主题文件——你删的是内容，不是索引。

7.5 有自动清理吗？

目前没有自动 prune 机制。 系统不会自动合并、删除、归档记忆。

用户需要手动管理 memory/ 目录：

  • 每 1-2 个月打开看一眼
  • 删除过时的（如"我们用 enzyme"——早就迁到 RTL 了）
  • 合并重复的（如两个反馈都说"不要加 emoji"）
  • 缩短过长的 hook 描述（保持 ~150 字符）
实操建议：把 ~/.claude/projects/<项目>/memory/ 目录加进 Git，每月一次 git log --oneline memory/ 看变化（只读，不提交），发现问题就手动改。

8. 误删能恢复吗？跨机器同步吗？

主报告没提。这是"产品边界"问题——记忆是本机的还是云端的？误删能不能 undo？换电脑了记忆会不会丢？

8.1 跨机器同步吗？

简短答案：不跨机器同步。

记忆存在本地文件系统：~/.claude/（getMemoryBaseDir() 默认返回 getClaudeConfigHomeDir()）。没有内置的云端同步或网络同步机制。

实际表现：

  • 在 A 机器写的记忆，换到 B 机器后不存在
  • 除非手动迁移 ~/.claude/ 目录
  • Cowork（CCR 远程模式）通过 CLAUDE_CODE_REMOTE_MEMORY_DIR 环境变量把记忆目录重定向到远程挂载点——这是通过文件系统挂载实现的同步，不是应用层同步

8.2 误删能恢复吗？

没有内置 undo 机制。

具体场景：

  • 删除了某个记忆 .md 文件：没有自动恢复。如果你启用了系统级 Time Machine / iCloud Drive / 文件历史，可以从那里恢复——但这不在 Claude Code 代码里
  • 删除了 MEMORY.md 索引：对应的 .md 文件还在磁盘上，只是索引空了。下次系统会创建新的（空的）MEMORY.md，丢失的只是索引指针，但内容可以靠子目录里的文件重建

恢复手段都在代码库外部：

  • 版本控制（如果你把 memory/ 加进 Git）
  • 系统备份（Time Machine / Windows File History）
  • 云盘同步（如果你把 ~/.claude/ 放 iCloud Drive / OneDrive 同步目录）

8.3 团队记忆怎么协作？

团队记忆（memory/team/）通过 TEAMMEM feature 在用户间同步——但具体同步机制是 Cowork/CCR 的应用层同步（不在 Claude Code 核心代码里）。

对于不开 TEAMMEM 的团队，可以把 .claude/agent-memory/（project scope 的子代理记忆）commit 进 git，让所有协作者共享——这是 推荐做法，主报告 §3.3 提过。

8.4 时区、编码、文件权限问题？

记忆文件是普通 UTF-8 markdown，所以：

  • 中文内容：✅ 支持（frontmatter 用 name: 中文名 即可）
  • 时区：日期时间戳是 ISO 8601（YYYY-MM-DDTHH:MM:SSZ），用 UTC。显示时按本地时区
  • 权限：默认 ~/.claude/ 目录的用户权限。如果多用户共用一台电脑，会互相读到对方的记忆——所以 Cowork/CCR 模式下会用 CLAUDE_CODE_REMOTE_MEMORY_DIR 隔离
实操建议：
  • 新机器：scp -r old:~/.claude/ new:~/.claude/ 迁移整个目录（关 Claude Code 时做）
  • 误删预防：把 ~/.claude/ 加进系统级 Time Machine / iCloud Drive
  • 团队协作：把 <项目根>/.claude/agent-memory/ commit 进 git，所有人共享
